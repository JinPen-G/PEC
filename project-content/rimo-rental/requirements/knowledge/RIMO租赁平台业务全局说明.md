## 1. 文档定位

本文用于让后续协作 RIMO 租赁平台的产品、设计、开发或 AI，快速理解平台的业务架构、多客户端关系、多租户机制、业务线划分、会员与企业身份、车辆与据点、订单与账单、价格与行销、以及当前重点规划中的门市租赁业务。

本文是平台级入口文档。后续处理任一业务线需求时，需要先阅读本文，再阅读对应业务线的 PRD、HTML 原型和专题业务说明。

重要业务逻辑或功能调整需要直接同步本业务知识库、对应业务线说明、相关 PRD 与原型；被修改文档的“版本更新记录”需要记录变更摘要，不再维护独立的业务决策记录文件。

当前平台已经上线的业务线：

- 分时租赁：同站租还
- 分时租赁：甲租乙还
- 公务用车

当前重点规划中的业务线：

- 门市租赁：门市租车
- 门市租赁：24 小时自助租车

合作通路租車券不是独立业务线，而是分时租赁下可挂接同站租还与甲租乙还的功能能力。当前一期 PRD 仅实现同站租还；甲租乙还扩展需要另行明确批次取还据点、费用、库存和订单校验规则后再纳入实施。

## 2. 平台整体架构

RIMO 是 SaaS 化租车平台。平台按客户端与业务职责分为客服系统、营运平台、企业端和前台应用。

### 2.1 客服系统

客服系统是平台方内部使用的租户管理系统，独立部署在台湾服务器。客服系统用于管理不同营运平台实例中的租户，也就是租车营运商。

客服系统是一对多管理结构。后续可以管理多个营运平台实例，例如台湾实例、新加坡 AWS 实例、欧盟实例。每个实例面向不同地区或不同资产隔离要求的客户。

客服系统新增租户时，先选择目标营运平台实例，再在该实例下创建租户。租户创建后归属于所选实例。

租户当前不支持从一个营运平台实例迁移到另一个营运平台实例，当前也没有跨实例迁移规划。后续如规划跨实例迁移，需要单独设计数据迁移、渠道配置、订单编号、车机设备、历史订单和企业账单的迁移规则。

客服系统主要能力：

- 新增和管理营运平台租户
- 配置租户所属国家或地区，并用于决定营运端地址模式
- 指定租户所属营运平台实例
- 授权租户可营运的业务线
- 配置租户各业务线订单编号前缀
- 配置租户接入的支付渠道
- 配置租户接入的短信渠道
- 配置租户接入的发票渠道
- 分配平台自有车机设备给租户

客服系统当前不进入租户业务数据，不查看营运平台中的订单、会员、车辆、账单、发票、退款等业务明细。客服系统只管理租户、实例、业务线授权、渠道和车机设备分配等平台管理资料。未来如客服系统需要查询租户业务数据，优先按远程 API 调用目标实例服务器数据处理，不把各实例业务数据同步或汇总到客服系统本地。

客服系统中的业务线授权当前主要控制营运平台相关业务线功能权限。未授权业务线的营运平台功能入口不展示，数据仍保留在系统中，但租户不能继续在营运平台营运该业务线。当前取消授权尚未同步隐藏 APP 服务入口，后续需要通过租户服务开关和接口级限制补齐前台入口控制。

客服系统授权业务线后，默认租户管理员账号具备对应业务线入口和功能权限；租户内其他账号需要在营运平台中配置角色并开启对应菜单权限和操作权限。

### 2.2 营运平台

营运平台是租车营运商日常使用的主体后台。每个实例服务器部署一套营运平台，实例下可以有多个租户。

同一实例服务器中的租户共用登录入口。租户用户登录营运平台时需要填写群组代码，也就是客户代码，用于识别当前登录的租户。

当前一个租户对应一个营运商主体。营运商可以与多个车行合作，但平台租户主体仍按一个营运商处理。

租户登录营运平台后，可以使用客服系统授权的业务线功能和平台基础功能。当前业务线授权后，营运平台默认展示对应业务菜单；未来规划增加租户自己的业务服务开关，由租户管理员在营运平台配置。

营运平台主要能力：

- 管理据点、车辆、车组、车型、车机、会员、企业客户
- 管理分时租赁、门市租赁、公务用车等业务线
- 配置各业务线标准价、行销方案、增值服务、租赁规则
- 处理订单、取还车、结算、退款、挂账、事故、调度
- 查看企业月结账单和业务统计

根据 2026-06-30 对营运端前端源码的读取，当时可确认的主业务模块包括订单管理、会员管理、车辆档案、车辆排程、车辆调度、车行 / 门市 / 据点、价格方案、行销方案、优惠券 / 兑换码、租赁业务规则、甲租乙还营运区域与调度费、企业客户、公务车合约、账务、经营统计、系统规则和地图轨迹。该内容只作为当时前端实现快照，不代表当前生产版本；客服、通知和工单属于附属支撑能力，不作为业务线主流程判断依据。

营运平台工作台定位为行动首页，用于聚合当前人员需要处理的业务任务、风险提醒和跳转入口，不作为综合分析 Dashboard。工作台内容需要按业务线、数据范围和功能权限渲染，不新增订单、车辆、站点或账单的独立业务状态。

营运平台中所有地址类页面，统一跟随租户所属国家或地区对应的地址模式渲染。当前平台地址模式只区分台湾模式和国际通用模式，不在营运端各页面单独提供国家可编辑选择器。

### 2.3 企业端

企业端是企业客户使用的平台。企业端用于管理员工企业身份、查看企业订单和账单，以及管理公务用车。

企业端登录也需要输入群组代码，对应到具体租户。企业客户如果同时与多个营运商合作，需要在不同租户下分别建立企业资料和企业会员方案；企业端登录后只查看当前群组代码对应租户的数据。

企业端当前账号类型包括总管理员和分公司管理员。员工审核、企业订单查看、账单查看与确认、公务用车管理等能力，按总管理员和分公司管理员的账号权限处理。

企业端主要能力：

- 审核员工加入企业的申请
- 查看员工使用企业身份产生的分时租赁订单
- 查看员工使用企业身份产生的门市租赁订单
- 查看企业月结账单
- 查看非月结企业身份订单，作为员工报销查询依据
- 管理绑定到公务用车合约配额下的车辆
- 新增公务用车辆并维护车辆签约企业 / 资产归属和车辆所在据点
- 上架、下架企业公务用车辆
- 配置企业通用或分公司专用的公务用车清洁保养提醒母版并套用到车辆
- 查看公务用车清洁保养提醒并登记已完成
- 查看公务用车预约记录
- 查看公务用车合约账单

企业端不能自行新建正式公务用车合约。公务用车合约、配额、实际用车企业、结算代付方、单车单价和合约有效期由营运端建立和维护；企业端使用营运端建立好的有效合约配额进行车辆绑定、上架、预约和账单查看。

公务用车车辆资料需要区分签约企业 / 资产归属和车辆所在据点。签约企业表达车辆资产归属，可以在分公司之间调整，但仅企业总管理员可操作；分公司管理员只能新增和维护资产归属为本分公司的车辆基础资料，不能修改签约企业 / 资产归属，不能把车辆调拨给其他分公司。车辆所在据点表达车辆实际停放位置，企业端可以在已配置的公务用车据点范围内直接调整。车辆调拨后，原分公司合约绑定失效，需要由新资产归属分公司重新选择本分公司可用合约并占用对应配额。员工可预约车辆范围以员工所属分公司的可用据点为核心判断条件：只要车辆当前所在据点属于该分公司的可用据点，且车辆已上架、状态可用、预约时间不冲突，该分公司员工即可预约该据点内车辆，不要求车辆资产归属也属于该分公司。公务用车订单和使用统计按员工所属分公司归属，车辆资产归属只决定车辆管理权限、合约绑定和清洁保养母版可选范围。

公务用车可用据点初始由营运端配置为企业签约范围内的全部公务用车据点，再由企业总管理员在建立分公司时为每个分公司分配可用据点。同一据点可以被多个分公司共用。车辆调拨、车辆所在据点调整、车辆下架、合约到期或合约失效均不自动取消已创建预约；已预约订单继续按订单创建时保存的车辆、据点、时间和历史快照处理，企业内部自行协调既有预约履约。公务用车当前实际场景暂未接入车机时，按预约管理和人工交付模式闭环；未来绑定车机后，员工可在公务用车 APP 执行开锁和还车动作。

公务用车预约本期不设置统一固定时长限制，允许跨天预约、立即用车、提前还车和延长用车。分公司后台可以开启预约用车审核；开启后员工提交预约申请，系统推送给员工部门主管审批，分公司管理员后台也可以审核。未开启审核时，员工提交后在车辆可用、据点可用、时间不冲突的前提下直接创建预约。公务用车订单类通知发送给预约员工，管理员后台主要接收员工加入企业审批、合约续费和合约到期提醒。

企业端的账单分为两类：

- 企业月结租赁账单：来自分时租赁、门市租赁等月结订单
- 公务用车账单：来自公务用车合约、配额、月缴或年缴单车单价

### 2.4 前台应用

前台应用是用户和员工实际下单、预约、取还车的界面层。前台应用只负责展示和用户操作入口，核心业务判断、计费、状态流转、权限校验均在后端完成。

前台应用包括：

- 公开消费者 APP
- 企业内部公务用车 APP
- 后续可能接入的官网下单入口

公开消费者 APP 面向个人会员和拥有企业身份的用户。用户可以用个人身份或企业身份使用租赁服务。

当前前台仍可按营运商独立 APP 或独立官网入口提供服务。统一 APP 多租户切换能力已经开始推进，后续公开消费者 APP 需要支持用户在统一 APP 内切换租户或营运商入口；但业务数据、会员账户、企业关系、积分、优惠券、订单和账单仍按租户隔离，不因为统一 APP 入口而合并。

企业内部公务用车 APP 面向企业员工。未加入企业或未通过企业审核的用户，无法正常使用公务用车 APP，也看不到公务用车车辆。

官网下单入口与 APP 本质相同，都是通过 API 串接后台能力。

## 3. 多租户、实例与业务授权

### 3.1 实例与租户

平台可以存在多个营运平台实例。一个营运商在不同实例中开通租户时，按不同客户处理。不同实例和租户通常也会对应不同地区、资产和营运隔离要求。

全局设计时不需要把跨实例的同一营运商品牌强行视为同一客户。产品侧按租户维度设计业务能力即可。

当前不支持租户跨实例迁移，当前也没有跨实例迁移规划。已创建租户、订单、账单、渠道配置和车机设备均按当前实例归属处理。

当前一个租户对应一个营运商主体。营运商可以与多个车行合作，车行作为营运商下的组织或合作资源管理，不等同于多个租户主体。

租户被客服系统停用或冻结后，该租户用户不能登录营运平台等租户后台。租户停用或冻结不删除历史数据，已创建订单、账单、发票、退款等业务数据继续保留；未恢复前，租户侧不能继续办理订单、账单、发票和退款等后台操作。

### 3.2 业务线授权

客服系统对租户进行业务线授权。授权时需要设置该租户在对应业务线下的订单编号前缀。

订单编号规则为：

- 每条业务线有独立前缀
- 前缀后面的编号规则统一
- 业务线前缀由客服系统在授权该业务线时配置

业务线订单编号前缀授权后允许修改。历史订单继续保留下单时使用的旧前缀，不能因后续前缀修改而改变历史订单号。

当前业务线授权口径：

- 客服系统已授权：营运平台展示对应业务线菜单，默认租户管理员账号具备对应功能
- 客服系统未授权：营运平台隐藏对应业务线菜单和功能
- 取消授权后：营运平台入口隐藏，历史数据保留，但租户不能继续在营运平台营运该业务线；当前 APP 服务入口尚未因此自动隐藏
- 租户内非管理员账号：需要通过角色配置开启对应菜单权限和操作权限

租户自己的业务服务开关当前尚未实现，未来规划增加，并由租户管理员在营运平台配置。届时控制关系为两层：

- 客服系统授权控制租户是否具备该业务线能力
- 租户服务开关控制具体服务模式是否对用户开放

租户服务开关按具体业务模式配置，不只按业务大类配置。可配置的典型服务模式包括同站租还、甲租乙还、门市租车、24 小时自助租车、公务用车。

未来租户服务开关实现后，租户关闭某个服务模式时，APP 和官网隐藏该服务模式的下单入口，营运平台不允许新建该服务模式订单。已创建订单不受影响，仍按原订单规则继续履约、结算、退款、挂账和查看。历史订单、价格、行销方案、账单和操作记录继续保留。当前 API 暂不做服务模式关闭拦截，后续需要增加接口级限制，避免绕过前端入口创建已关闭服务的订单。

订单不需要保存租户服务开关状态。订单能够创建成功，代表创建时对应业务线已授权且服务模式处于可用状态。订单仍需保存业务线、业务模式、订单编号前缀、规则版本和业务快照。

### 3.3 渠道与发票配置

支付、短信、发票渠道当前按租户级配置，并由客服系统为租户配置。营运平台租户管理员当前不自行配置支付、短信和发票渠道。

支付渠道口径：

- 当前单个租户实际只使用一个支付渠道
- 后续规划支持租户启用多家支付渠道
- 后续多支付渠道上线后，用户付款或预授权时可以自行选择支付渠道，后台操作收款或预授权时也可以由操作人选择支付渠道
- 每笔支付、预授权、退款交易都需要记录本次交易使用的支付渠道
- 预授权和实际支付不要求使用同一家支付渠道；下单预授权使用 A 渠道时，后续取车补尾款可以使用 B 渠道
- 租户如需新增接入自己使用的支付平台，由客服系统配置接入
- 支付渠道仍按租户级管理，当前不按业务线、门店或企业客户拆分渠道配置

短信和发票渠道也按租户统一配置，并由客服系统维护。

发票开立口径：

- 个人自付订单和企业非月结订单按支付记录开票，一笔支付对应一张发票。
- 个人自付订单和企业非月结订单暂不支持部分开票或拆开发票，系统在支付成功后按支付记录自动执行开票。
- 企业月结订单按月度账单开票，企业账单付款完成后由人工上传账单发票。
- 公务用车账单按公务用车合约账单付款结果开票。
- 开票金额按客户实际支付金额计算。积分抵扣、优惠券抵扣和减免不计入客户实际支付金额。
- 发生退款时，RIMO 平台只同步退款记录给发票平台。发票作废、红冲、折让或其他后续处理由发票平台按自身规则处理。RIMO 平台不在 PRD 中定义发票平台内部处理规则。

### 3.4 车机设备分配

车机设备是平台公司自有设备，不允许租户在营运平台随意新增。

车机设备流程：

1. 客服系统将车机设备分配给租户
2. 租户在营运平台中看到可用车机
3. 租户将车机绑定到具体车辆

营运平台不能将车机设备退回客服系统库存。只有客服系统删除或取消分配该车机后，营运平台才不再显示该车机。

分时租赁和 24 小时自助租车必须绑定车机后才允许上架给用户预约。门市租车由店员服务取还车，可以无车机运行；公务用车可以不绑定车机，仅作为预约管理使用。

车辆已绑定车机但车机离线、低电或指令失败时，不阻断新预约。已预约订单继续保留，但取车或还车环节会因车机异常被阻断，需要提示营运人员处理。

## 4. 业务线分类

平台业务线按业务形态分为分时租赁、门市租赁和公务用车。

| 大类   | 业务模式      | 当前状态 | 核心特点                     |
| ---- | --------- | ---- | ------------------------ |
| 分时租赁 | 同站租还      | 已上线  | 用户选择具体车辆，同一据点取还          |
| 分时租赁 | 甲租乙还      | 已上线  | 用户选择具体车辆，不同据点取还，涉及地区调度费用 |
| 门市租赁 | 门市租车      | 规划中  | 有店员服务取还车，按车组预约           |
| 门市租赁 | 24 小时自助租车 | 规划中  | APP 自助取还车，按车组预约          |
| 公务用车 | 企业公务用车    | 已上线  | 企业内部车辆预约和管理，不涉及员工支付      |

合作通路租車券不在业务线表中单列。该功能属于分时租赁，可按服务模式扩展到同站租还或甲租乙还；当前一期仍以同站租还为实现范围。

### 4.1 分时租赁

分时租赁包含同站租还和甲租乙还。用户在 APP 下单时选择具体车辆，不选择车组，也不选择车型。

分时租赁使用同一套车组基础资料，但同站租还和甲租乙还的标准价、行销方案、增值服务当前相互独立。

分时租赁当前 APP 是两个入口：同站租还、甲租乙还。未来可以整合为一个分时租赁入口，再在入口内选择服务模式。

### 4.2 门市租赁

门市租赁包含门市租车和 24 小时自助租车。

门市租车和 24 小时自助租车共用：

- 车组
- 标准价
- 动态调价
- 行销方案
- 增值服务
- 租赁业务规则
- 计费规则
- 用车过程中的 APP 功能

两种模式的主要差异是取还车方式：

- 门市租车：由店员服务取车、还车、验车、收款、结算
- 24 小时自助租车：用户在 APP 中自助取车、还车、验车和完成相关操作

门市租赁主要面向 APP 公开预约，也支持官网下单和营运后台代下单。官网和 APP 都通过 API 串接后台。

### 4.3 公务用车

公务用车是企业内部车辆预约和管理业务。

公务用车不涉及员工个人支付。营运商为企业建立公务用车相关据点、配置公务用车合约、设置可管理车辆配额、设置月缴或年缴单车单价。企业在企业端建立内部车辆信息，绑定有效公务用车合约配额后，可以上架给员工预约。

公务用车车辆可以是企业自有车辆，也可以是营运商提供给企业使用的车辆。

公务用车合约类型分为试用合约和正式合约。试用和正式是两类独立合约，不再把试用期作为正式合约开始前的一段附属期间处理。

公务用车合约需要记录实际用车企业和结算代付方。结算代付方可以与实际用车企业一致，也可以选择第三方付款。实际用车企业用于员工用车、车辆归属和企业端业务管理；结算代付方用于公务用车合约账单的付款归属和收款核对。

公务用车合约到期后，系统强制将企业绑定在该合约下的公务用车下架，不再提供员工预约使用。

历史资料中出现的“短租订阅”不再作为当前独立业务线处理。短租订阅后续业务定义已经调整为当前公务用车业务，涉及企业车辆配额、企业内部预约、合约账单和续费时，统一按公务用车业务口径处理。

## 5. 用户、会员、企业与身份

### 5.1 用户身份

用户注册后默认为个人会员。用户可以在 APP 中申请加入企业。企业在企业端审核通过后，用户获得该企业身份。

会员账户按租户完全隔离。同一个手机号在不同租户下，是不同的会员账户，会员方案、企业关系、积分、优惠券和订单数据均相互独立。当前不做跨租户会员合并、跨租户积分合并或跨租户黑名单联动。

用户首先是个人消费者，其次才是企业员工。即使用户所在企业未签约某项服务，用户仍可以使用个人身份预约该服务。

当前用户在同一租户内只能加入一个企业。下单时用户手动选择个人身份或企业身份，系统默认使用个人身份，不用上一次下单身份作为默认值，避免用户误用企业资格下单。

企业员工状态需要区分离职停用和删除账号记录。离职停用后，历史订单和未完成订单保留原企业关系记录，企业端仍可按历史关系查看对应订单。企业内部删除该员工账号记录后，该离职员工的用车订单不再与该企业建立当前员工关系，但订单自身的历史快照和费用记录继续保留。

下单时需要确定用户使用的身份：

- 个人身份
- 企业身份

身份会影响会员方案、可用行销方案、支付方式、月结资格和企业端展示。

### 5.2 会员方案

会员方案是平台级共用能力概念，具体会员账户、会员方案绑定、积分、优惠券和企业关系按租户隔离。

会员方案分为：

- 个人会员方案
- 企业会员方案

营运商可以配置多个个人会员方案，并设置其中一个作为默认个人会员方案。用户注册后默认绑定该默认个人会员方案，后续可以按营运规则调整。

企业客户按租户完全隔离。同一个企业客户如果与多个营运商合作，需要在每个租户下分别建立企业资料并绑定企业会员方案。每个企业在当前租户内绑定一个企业会员方案。

会员方案会影响车辆可见性。车辆新建时可以设置为特殊车辆；特殊车辆开启后，需要选择允许查看和预约的会员方案，只有命中对应会员方案的用户才能在 APP 中看到并预约该车辆。

会员方案也会影响甲租乙还的预约后订单有效期和短时间取消限制规则。甲租乙还是实时性订单，预约后可能需要在 30 分钟内取车，超过订单有效期未取车时系统自动取消订单。营运商可以按会员方案配置不同订单有效期，例如普通会员 30 分钟，高级会员 40 分钟或 50 分钟。短时间取消限制也按会员方案配置，例如普通会员 2 小时内取消 2 次后限制 2 小时预约，高级会员可配置为 4 小时内取消 4 次后限制 1 小时预约。

订单创建成功后，订单按下单时的会员方案权益和规则快照执行。用户会员方案后续到期、切换或被管理员强制解除，不反向影响已创建但未履约完成的订单。

个人会员方案可以是免费方案，也可以是收费方案。收费方案支持月缴、季缴、半年缴和年缴。会员方案中配置的缴费金额是默认金额：

- 用户在 APP 申请从免费方案切换到收费方案时，按方案默认金额收费。
- 后台管理人员为用户切换到收费方案时，系统带出默认金额，管理人员可以修改实际收费金额。
- 免费方案切换到收费方案时，支付成功后立即生效。
- 收费方案切换到收费方案或免费方案时，默认等当前已收费周期到期后自动切换。
- 后台管理人员可以强制解除用户当前会员方案绑定，并恢复到默认个人会员方案。
- 后台管理人员可以设置用户会员方案是否自动续费。
- 不自动续费的会员方案到期后，用户自动恢复成默认个人会员方案。
- 自动续费成功后刷新会员方案有效期。
- 自动续费失败时，当前系统会将用户账户停权。后续可规划为租户配置项，由营运商选择续费失败后恢复默认方案或停权。

后台管理人员强制解除用户会员方案时，只处理会员方案绑定关系变更，不自动执行会员费退款。涉及会员费退款时，由管理员在会员费收费单中手动发起退款。

企业会员方案当前主要用于行销方案匹配。不同企业绑定不同企业方案后，可以匹配各自专属的行销优惠方案；企业方案暂不影响押金、风控、账单规则或服务费。

### 5.3 行销方案匹配

行销方案在创建时配置适用条件，包括：

- 适用会员方案
- 有效时间
- 适用据点
- 适用车型、车组或车辆范围
- 适用业务模式
- 其他业务线自己的匹配条件

用户下单时，系统先判断用户使用个人身份还是企业身份，再找到该身份对应的会员方案，然后匹配符合条件的行销方案。

如果有可用行销方案，APP 展示所有可用方案给用户选择。订单最终使用一个行销方案，不自动叠加多个行销方案。分时租赁当前默认选中最终价格最低的方案；门市租赁也按最终价格最低的方案作为默认选中方案。没有可用行销方案时，使用标准价。

门市租车存在到店证件和资质复核。用户在 APP 或官网选择低价行销方案后，如果门店取车时检查发现证件、资格或适用条件不符合，店员可以在取车流程中调整行销方案，并保存调整原因和操作记录。

### 5.4 优惠券与积分点数

平台已有优惠券和积分点数能力。优惠券可以配置可用服务范围和适用会员方案。

优惠券优惠类型包括：

- 租金折扣：例如租金 7 折。
- 租金现金减免：例如租金减 200。
- 租用时数减免：在实际用车时数基础上减去指定时数，再计算租金，得出减免金额。
- 折抵里程：在实际用车里程基础上减去指定里程，再计算最终里程费。

积分点数有有效期限。积分获取方式包括：

- 用户注册赠送。
- 邀请他人赠送。
- 同站租还订单提前还车时，不退租金，按规则退还积分。
- 参加活动获得积分。
- 营运人员后台发放积分。

行销方案和优惠券可以同时使用。优惠券和积分点数是否可以同时使用，由管理员在新建优惠券时配置。费用计算顺序为：标准价 -> 行销方案 -> 积分点数 -> 优惠券。积分点数抵扣上限不得超过订单纯租金，不包含增值服务费、调度费、车损、清洁费等非租金费用。

租用时数减免和折抵里程优惠券适用于分时租赁和门市租赁。门市租车也支持折抵里程，用于还车结算时抵扣实际超里程费用。

同站租还提前还车不退租金，按后台配置的百分比退还积分，不按未使用金额等值退还。分时租赁基本不涉及现金退款。门市租车提前还车按规则判断是否可退；可退金额走人工退款或还车结算抵扣，暂不使用提前还车退积分规则。

当前已上线分时租赁中，企业身份订单仍支持优惠券和积分点数能力。优惠券和积分点数是否可用，按对应优惠券、积分规则和适用会员方案判断；企业月结和企业非月结订单均按当前系统能力处理。

平台未来规划中，企业身份订单不再支持优惠券和积分点数。门市租赁等新增规划业务按未来口径处理：企业身份订单只使用企业会员方案匹配到的行销方案，不展示优惠券和积分抵扣入口。

### 5.5 企业签约服务类型

企业客户新增时，营运商需要选择该企业签约的服务类型。

企业签约服务类型控制员工能否使用企业身份预约对应服务。企业未签约某服务时，员工仍可用个人身份预约该服务，但不能用该企业身份预约。

例如：

- 企业签约分时租赁，员工可以用企业身份预约分时租赁
- 企业未签约门市租赁，员工不能用企业身份预约门市租赁
- 员工仍可以用个人身份预约门市租赁

### 5.6 企业月结与非月结

企业身份订单分为企业月结和企业非月结。

企业月结订单：

- 不走个人支付
- 不收个人预授权
- 不发起个人退款
- 订单费用进入企业月结账单
- 当前企业月结只按企业维度汇总，不按员工、部门或项目拆分账单
- 基础订单费用按还车结算确认并生成月结挂账交易记录的时间进入对应自然月账单；订单完成后的追加费用、补录事故费用、追缴、退款、费用调整或账单调整，按对应费用确认并生成月结挂账或调整交易记录的时间入账，不回改原订单完成月份或已关闭账期
- 当前已上线分时租赁仍可按优惠券、积分和会员方案规则使用优惠券或积分；未来规划不再支持

企业非月结订单：

- 使用企业身份和企业资格计费
- 费用由员工个人支付
- 企业端可以查看订单
- 不进入企业月结账单
- 可作为员工后续报销查询依据
- 可在企业端导出，供员工报销或企业内部核对
- 当前已上线分时租赁仍可按优惠券、积分和会员方案规则使用优惠券或积分；未来规划不再支持

门市租赁属于新增规划业务，企业月结和企业非月结均按未来口径处理，不支持优惠券和积分点数。

## 6. 据点、车辆、车型与车组

### 6.1 据点

当前服务站点层级为：车行 -> 门市 -> 据点。

车行是营运商下的合作资源或组织管理层级，不作为对用户展示的品牌主体。门市是面向客户服务和门店人员作业的组织层级，据点是具体实体物理站点，通常对应停车场、停车区域、自助取还车点或车辆实际停放位置。

车行是车辆资产归属、同车行调度及经营归集边界。当前尚未上线营运商与合作车行之间的系统结算，双方结算仍在线下处理；系统订单、用户端品牌展示和对外服务使用营运商品牌，车辆实际资产可以属于合作车行。

一个门市只能属于一个车行。一个据点只能属于一个门市。据点按实体物理站点建立，一个门市下可以有多个据点。一个实体据点可以具备多种服务能力。服务能力按具体业务模式配置，例如同站租还、甲租乙还、门市租车、24 小时自助租车、公务用车分别开关。

服务站点管理按“一个实体据点，多种服务能力”改造。服务能力区分“是否具备服务能力”和“服务状态”。未具备服务能力时，新订单、新预约和车辆上架不能选择该据点作为对应业务模式的服务据点；已具备但服务状态为暂停时，保留配置和历史数据，但不再对该服务模式的新订单或新预约展示。本期只定义改造后的新模型和新页面行为，不处理历史旧据点合并和旧订单回溯修正。上线时需要做最小数据初始化，将既有据点原服务类型转换为对应服务能力，确保新查询接口可以继续查到原有据点。

车行、门市和据点分别使用独立管理页面。车行页面维护资产归属与数据范围；门市页面维护客户服务组织、营业时间和店员履约信息；据点页面维护实体停车位置、地址、坐标、车位和各服务模式能力。据点页面左侧的车行 / 门市树只用于数据筛选，不承担车行或门市新增、编辑功能。

服务据点页面分为“据点总览”和“服务能力管理”两个视图。据点总览一行对应一个实体据点；服务能力管理一行对应一个“据点 + 服务模式”能力记录。同一据点同一服务模式只能存在一条能力记录。基础据点停用后，所有服务模式均不得接受新预约或新订单；单项服务能力暂停时，只影响该服务模式，历史订单不自动取消。

据点权限由数据范围、功能权限和服务模式权限共同决定。“据点总览查看 / 维护”与“同站租还、甲租乙还、门市租车、24 小时自助租车、公务用车”的查看 / 维护权限分别配置。账号没有据点总览权限、但拥有部分服务模式查看权限时，只展示服务能力管理并自动进入该视图，只能看到获授权服务模式的数据。车行账号仅处理本车行范围，门市账号仅处理本门市范围；只读、导出、新增、编辑、启停分别校验权限，后端必须在返回数据前完成过滤。

据点总车位是物理容量。各服务能力配置的预留车位之和不得超过据点总车位，超过时阻止保存。该约束不等同于实时可预约车辆数，实时预约仍需继续判断车辆状态、订单占用、服务能力和业务规则。

据点类型由营运端维护，可配置是否“一般预约开放”。普通同站租还和甲租乙还入口只展示据点类型一般预约开放、具备对应服务能力且服务状态启用的据点。合作通路租車券批次按适用据点类型和适用据点控制可用范围，可以选择一般预约可用或不开放一般预约的据点类型。

车辆当前挂在具体据点下，资产统计需要从据点上卷到门市和车行，用于营运商内部管理合作车行资产、车辆库存和车辆使用情况。分时租赁和门市租赁车辆所在据点变更必须通过调度或调拨流程处理，不在车辆资料页直接修改所属据点；公务用车车辆所在据点可由企业端在已配置公务用车据点范围内直接调整，用于企业内部车辆停放位置和员工可预约范围判断。

车辆资产所属车行不允许后期变更，不通过车辆资料编辑、订单派车、还车归位或普通调度流程修改。订单需要保存实际履约车辆的资产所属车行快照，后续车辆资料调整不得反向改变历史订单的车行结算归属。

例如同一个据点可以支持：

- 分时同站租还
- 分时甲租乙还
- 门市租车
- 24 小时自助租车
- 公务用车

每种服务能力可以有独立配置，包括营业时间、节假日规则、暂停服务时间、取还车规则、可用车辆范围、服务开关、费用规则等。甲租乙还服务能力启用后，默认同时支持作为取车据点和还车据点，不再单独配置取车或还车开关。

据点关闭某项服务能力后，新订单在预约时看不到该据点，无法选择该据点下单；已创建订单不因据点服务能力关闭而自动取消。还车场景中，甲租乙还需要实时查询可还车据点，因此关闭后的据点不会出现在甲租乙还可还车站点中，会影响已有甲租乙还订单选择该据点还车。

甲租乙还可还车据点判断，不仅要读取据点是否具备甲租乙还服务能力，还要继续读取当前可还车空闲车位。只有具备甲租乙还能力、服务状态启用且可还车空闲车位大于 0 的据点，才能返回给用户端作为可还车据点。

需要特别注意旧版 APP 兼容：甲租乙还旧版 APP 已经依赖可还车据点查询 API 中的空闲车位字段判断是否允许还车。本次服务站点能力模型改造后，后端不得改变该 API 空闲车位字段的业务含义、扣减时机、返回规则或空位为 0 时不可还车的判断逻辑，也不得仅按服务能力返回可还车据点，避免影响旧版 APP 的甲租乙还还车流程。

据点停用或暂停服务是独立于服务能力关闭的据点状态。当前据点停用后，预约时看不到该据点，无法选择该据点下单；还车不受据点停用状态影响。

门市租赁下的取还车点口径：

- 门市租车是店员服务模式，客户面向的是取车门市和还车门市。车辆仍然挂在门市下的具体据点，系统按门市下可用据点汇总库存和可派车辆。派车后订单列表和订单详情在取还站点信息中展示车辆当前所在据点，详情页格式为“门市 - 据点 - 地址”，列表无地址时展示为“门市 - 据点”。门店人员据此备车到门市交付区或指定交接点。车辆所在据点由已派车辆带出，不由店员手动选择。取车记录中保存服务门市、车辆所在据点、交付位置和实际车辆。
- 24 小时自助租车是用户自助模式，客户必须面向具体据点取还车。自助据点需要具备自助取还车服务能力、可到达地址、车位指引和必要的自助设备或操作条件。
- 24 小时自助租车允许还到同门市下所有具备 24 小时自助租车能力且服务状态启用的据点。同门市下不同自助据点还车不产生调度费。
- 门市租车还车时，客户归还给订单当前还车门市；只有订单当前还车门市默认拥有还车操作权限。门店人员完成验车后，再记录车辆最终停放的归还据点、楼层、车位和照片。门市租车异地还车费和调度费只按取车门市与订单当前还车门市是否一致判断，不按车辆所在据点或归还据点判断。客户或门店需要调整还车门市时，必须先执行“改还车门市/转单”，转单后新门市获得订单列表、详情和还车操作权限，并按新旧还车门市重新计算调度费差额。转单确认前检查原还车门市是否已有后续预约占用当前车辆，存在冲突时先快捷改派后续订单，释放后续占用后再完成转单。

门市租车本期只支持同车行内改还车门市/转单。跨车行改还车门市、跨车行转单和跨车行还车继续严格不开放，需要线下协调或作为后续独立功能规划；后续设计跨车行转单时，需要同时处理数据权限、车辆资产归属、门市操作权限和车行营收报表影响。

### 6.2 车辆基础车型

车辆基础车型用于描述真实车辆的基础属性，例如品牌、车系、车型、能源类型、座位数、车辆规格等。

例如 BMW 3 Series 属于车辆基础车型概念。

### 6.2.1 载具类型与会员可用载具

车辆和车组需要维护载具类型。当前载具类型至少包含汽车、摩托车和微电车。车型组、车辆、会员资料、会员审核、APP 预约校验和合作通路租車券车辆查询需要使用同一套载具类型枚举，页面文案统一使用“摩托车”，不使用“机车”。

会员资料需要保存“可用载具类型”。用户预约时，系统按所选车辆或车组对应车辆的载具类型，与会员资料中的可用载具类型校验是否允许预约。微电车默认不要求驾驶执照，也不要求上传驾驶执照资料；汽车、摩托车仍按现有驾驶执照资料、资质审核和会员资格规则处理。微电车免驾驶执照资料能力当前尚未完成实现，后续开发时需要同步会员资料、会员审核、会员详情、车型组、车辆查询和预约创建校验。

会员审核功能开启时，管理员在统一提交窗口中逐项审核基本资料、身份证、驾驶执照和手持证件自拍，四项默认选中“通过”，并在同一窗口选择会员可用载具类型。四项全部通过时调用原“审核通过”后端流程；任意一项不通过时调用原“审核不通过”后端流程，不通过类型由对应资料项自动带出，原因支持选择预设值或手动输入。驾驶执照审核通过时，即使其他资料项不通过，也保存本次选择的可用载具类型；只有驾驶执照审核不通过时，会员可用载具类型不更新并保留原值。普通驳回允许会员重新提交，单笔审核可标记高风险且不可复审，批量审核不提供高风险操作。会员审核功能关闭时，仅表示会员注册和修改资料不需要人工审核、系统默认通过资料提交；审核开关不作为载具资格放行开关，预约时仍需校验会员可用载具类型。

### 6.3 业务线车组

业务线车组是营运商为了定价、展示和库存管理进行的业务分组。

例如经济组、豪华组、SUV 组等。

分时租赁和门市租赁对车组的使用方式不同：

- 分时租赁：用户选择具体车辆，车组主要用于营运定价、归类和规则配置
- 门市租赁：用户按车组预约，后续由系统或门店分配具体车辆

分时租赁使用一套车组基础资料。门市租赁使用独立车组。

门市租车和 24 小时自助租车共用门市租赁车组。

### 6.4 车辆服务类型

当前车辆服务类型是单选。一台车在当前时间只属于一个业务线或服务类型。

车辆新建时选择服务类型。车辆资料编辑页不允许直接修改服务类型；服务类型只能通过调度相关功能变更。车辆切换服务类型时，需要同步选择新服务类型下的所属据点，并记录切换前后服务类型、切换前后据点、操作人、操作时间和切换原因。

车辆历史订单继续展示订单创建或履约当时的服务类型、所属据点和车辆信息快照，不读取车辆当前服务类型反向改写历史订单。

当前切换服务类型时，如果车辆存在未完成订单或未来预约，系统提示风险但允许具备权限的人员强制切换。切换后系统保留车辆已有未完成订单和未来预约，不自动取消，也不自动改派。现阶段不自动追加风险标记，后续订单影响由营运人员人工处理。

当前车辆资源按业务线隔离。需要通过调度或后台操作，将车辆变更到新的服务类型和对应据点。车辆当前位置可以记录到其他车行下的门市或据点，但这只表达实际停放位置或内部处理位置，不改变车辆资产所属车行，不代表车辆进入对方车行库存，也不形成跨车行订单派车能力。当前各车行车辆先独立，不做跨车行车辆调拨、跨车行库存池或跨车行车辆借调；门市租赁订单派车、订单改派和改还车门市当前只支持同车行范围。公务用车车辆与租赁车辆当前不允许互相转换服务类型。

车辆档案存在两条独立状态轴：是否启用和车辆营运状态。是否启用控制车辆是否允许参与新订单销售、自动派车、人工改派、硬锁定和确认发车；车辆被禁用后，不再进入新订单销售和调度候选池，但已经进入取车中、用车中、续租中、逾期未还、还车结算中的订单允许继续完成还车闭环。

车辆营运状态包括空闲、租用中、被管控中。空闲代表车辆当前可作为即时可交付车辆；租用中代表车辆正在被执行中的订单占用，不允许参与重叠时间窗的派车，但在前序订单和订单间隔结束后可以参与未来无冲突订单的预分配；被管控中覆盖清洁、保养、调度、还车待整备等内部处理场景，管控未解除前不得参与预分配、硬锁定和确认发车。公务用车套用同一套车辆营运状态。

门市租赁判断车辆是否可履约时，必须同时读取“是否启用 + 车辆营运状态 + 时间窗占用 + 派车状态/订单状态”，不能只读取单一车辆状态字段。

营运端车辆排程按车辆时间轴展示订单占用和内部管控占用。排程占用类型包括预约、取消、已取车、延期、逾期、完成、清洁、保养、维修和调度等。后续涉及派车、调度、改派、据点变更或车辆可用性判断时，需要统一读取车辆时间窗，不能只按车辆当前状态判断。

车辆清洁和保养是全平台车辆管理规则，不按业务线单独拆分。当前有单独车辆管控模块承载维修、事故、停运、失联、清洁、保养、整备等内部管控。车辆触发大清洁、小清洁、保养或其他整备任务时，需要生成对应任务或管控记录，并在管控期间进入被管控中，阻断分时租赁、门市租赁和公务用车的新预约与派车。

企业端可以为公务用车配置清洁保养提醒母版，并按企业名下车辆的当前里程、上次保养时间、上次清洁时间和已完成公务用车预约次数生成提醒。提醒母版支持企业通用和分公司专用两层；车辆只可绑定企业通用母版，或当前资产归属分公司的专用母版。企业总管理员可在“清洁保养提醒设定”标题后控制“是否启用分公司专用”；新增母版时，企业总管理员默认创建企业通用母版，分公司管理员默认创建当前分公司的分公司专用母版。如“是否启用分公司专用”关闭，分公司管理员不显示新增母版按钮，只可查看母版表和设定资产归属为本分公司的车辆套用。车辆资产归属分公司变更后，如原绑定的是旧分公司专用母版，系统自动清空对应绑定并标记资料待补。该能力本期只产生提醒和完成登记，不直接生成工单、不直接把车辆切换为被管控中、不直接阻断员工预约。是否进入车辆管控，仍由平台统一车辆管控模块处理。

车辆已被预约后，如果后续进入维修、事故、停运、失联或其他不可用状态，系统不自动取消订单，也不自动改派；由营运人员人工处理改派、取消或联系客户。

未来规划方向是同一台车辆可以同时支持多个业务线，通过排程占用解决跨业务线车辆冲突。跨业务线车辆共用时，价格、行销方案、增值服务和规则仍按订单所属业务线计算，不受车辆上一笔服务类型影响。

跨业务线车辆共用的长期目标是统一排程中心。统一排程中心按车辆维度展示所有业务线订单和预约占用，分时租赁、门市租赁、公务用车等业务都占用同一台车的时间轴。统一排程中心在门市租赁开发完成后再规划和开发。本期仍按车辆服务类型隔离，不实现跨业务线统一排程。统一排程中心的占用类型和业务优先级当前暂未定义，后续规划统一排程中心时再单独设计。

## 7. 价格、行销与增值服务

### 7.1 分时租赁价格

分时租赁同站租还和甲租乙还使用同一套车组基础资料，但标准价分业务线独立配置。

分时租赁标准价区分平日和假日。

分时租赁当前计费机制为后付费：

1. 用户预约时按租金倍率收取预授权
2. 用户还车后按实际用车情况计算最终费用
3. 系统从预授权额度中扣款
4. 企业月结订单不收个人预授权，最终费用进入企业月结账单

预授权倍率由营运商在后台设置。

分时租赁预约时发起预授权。预授权失败时，分时租赁订单不进入待支付保留，订单直接记录为 `rejected` 或被拒绝状态，并释放车辆资源。

门市租赁下单时发起预授权押金。预授权金额严格执行租赁业务规则配置，支持固定金额或租金百分比；百分比模式本期不允许超过 100%，预授权金额不超过租金。下单阶段的预授权押金本期统一线上预授权，不支持现金押金、线下押金或仅登记线下凭证。门市租赁预授权失败时，订单进入 `pending_payment` 待支付状态，并在资源保留时长内允许客户或门店重新发起线上预授权；保留超时后取消订单并释放库存。

门市租赁预授权在取车时已经完成转租金、释放或履约担保处理，不单独设计取车后的预授权到期处理。分时租赁预授权到期后，订单仍按实际费用生成扣款、补缴或追缴记录；预授权主要用于预约兜底，降低用户无可用额度却占用车辆资源的风险，不作为唯一收款手段。

### 7.2 分时租赁行销方案

分时租赁当前同站租还和甲租乙还的行销方案完全区分。

行销方案设置具体车组的平日价格和假日价格，并配置适用会员方案、有效时间、适用据点、适用车型或车辆范围等条件。

未来规划方向是将分时租赁行销方案归为一个大类。一个分时行销方案可以配置适用于同站租还、甲租乙还或两者同时适用，但不跨到门市租赁。

### 7.3 门市租赁价格

门市租赁包含门市租车和 24 小时自助租车。两种模式共用车组、标准价、动态调价、行销方案、增值服务和业务规则。

门市租赁标准价按车组统一配置，不区分平日和假日。

门市租赁行销方案在标准价基础上进行优惠。行销方案可以配置平日和假日不同优惠价或折扣价。

若门市租赁订单关联的门市或据点在订单创建后关闭或暂停，后台和 APP 只展示据点状态与“据点已关闭，请联系客服处理”或“据点已暂停，请联系客服处理”提示，本期不自动改站、不自动转单、不自动取消，由客服人工处理。24 小时自助订单需要支持改还车据点；若据点跨门市，仍按门市口径处理权限、冲突校验和异地还车费差额。

门市租赁起租按 24 小时计算。超过完整 24 小时后的剩余用车时长：

- 不足 1 小时按 1 小时计
- 每超过 1 小时按牌价的 10% 计
- 从第 5 小时起按 1 天计

跨平日、假日时，按每一轮 24 小时周期的起始时间判断该周期适用平日价或假日价。

### 7.4 增值服务

增值服务未来按大类隔离：

- 分时租赁增值服务
- 门市租赁增值服务

同一个增值服务大类下，可以配置适用的业务模式、会员方案、据点、车辆或车组条件。

分时租赁与门市租赁的增值服务不跨大类共用。

### 7.5 收费项目与费用归类

营运端存在收费项目配置，用于维护费用名称、会计科目、是否开票和计费顺序。收费项目不是单独的价格方案，也不决定某项费用是否发生；它用于订单费用明细、财务核对、开票归类和报表统计。

后续新增费用类型时，需要同时明确：

- 费用由哪个业务动作触发
- 费用适用哪些业务线或业务模式
- 费用是否进入租金、调度费、事故费、清洁费、车损费、违章费、油电差额或其他费用分类
- 费用是否开票
- 费用是否进入企业月结、合作通路挂账或公务车合约账单
- 费用是否影响车行结算和经营报表

## 8. 订单与账单

### 8.1 订单入口

当前各业务线订单列表是拆开的。

后续订单入口按业务大类规划。分时租赁设置一个订单菜单，页面内用 Tab 区分同站租还和甲租乙还。门市租赁设置一个订单菜单，页面内用 Tab 区分门市租车和 24 小时自助租车。

如果某个业务模式后续状态差异、处理流程或批量操作差异过大，可以在业务大类菜单下继续拆分子页面，但平台整体导航优先保持按业务大类聚合。

### 8.1.1 公开租赁未完成订单卡控

公开租赁业务的未完成订单卡控统一适用于同站租还、甲租乙还、门市租车和 24 小时自助租车。

用户存在未完成公开租赁订单时，新建同站租还、甲租乙还、门市租车或 24 小时自助租车订单需要按统一卡控规则处理，避免同一用户在公开租赁业务中并行占用多个未完成用车流程。

公务用车员工预约不纳入公开租赁未完成订单卡控口径。

### 8.2 订单编号

每条业务线有自己的订单编号前缀。前缀由客服系统在授权租户业务线时配置。

前缀后面的编号规则统一。

订单编号需要能识别业务线来源，便于客服、营运、财务、企业客户和用户核对。

### 8.3 订单快照

订单必须保存下单时的关键业务快照，不得只保存基础资料 ID 后实时读取当前名称。

需要保存快照的典型内容：

- 租户信息
- 业务线和业务模式
- 门店、据点名称
- 客户信息
- 企业信息
- 会员方案
- 行销方案
- 车组、车型、车辆信息
- 标准价、动态调价、服务产品
- 业务规则版本
- 费用计算结果
- 支付或月结口径

后续基础资料改名、车组改名、门店改名、企业名称调整、价格规则调整时，不得影响历史订单展示和核对。

门市租赁采用“订单级基线快照 + 事件级增量快照”模型。下单时固化原订单商业快照，作为合同基线；后续事件中，仅涉及履约分配、不改变用户商业承诺的，继续读取订单基线快照；涉及租期、车组、行销方案、价格规则、税费口径等商业条件变化的，必须生成事件级增量快照，并按事件发生时命中的版本结算差额，不覆盖原订单快照。老订单保护保护的是订单基线快照，不是保护后续续租、改租期、改车组、到店改方案或逾时重计费继续沿用下单时旧版本。

### 8.4 企业账单

企业月结账单当前只按企业维度和自然月汇总，不按员工、部门或项目拆分账单。企业月结订单归属月份按订单实际还车完成时间判断，实际还车后才能确定订单最终费用并进入对应自然月账单。当前只有分时租赁时，企业端展示一张企业月结总账单，账单内区分不同类型订单。

后续门市租赁月结订单也可以融入同一张企业月结账单，并在账单内按业务线和订单类型展示明细。

进入企业月结账单的统一规则：

- 订单使用企业身份
- 该企业订单为月结
- 订单费用应由企业月结承担

企业非月结订单不进入企业账单，但企业端可以查看和导出，作为员工报销查询依据。

企业月结账单当前按订单金额实时统计，尚未实现企业确认账单功能。后续企业月结账单需要覆盖完整账单状态，规划设计时需要补全至少以下状态口径：

- 待出账
- 已出账
- 待企业确认
- 已确认
- 待付款
- 已付款
- 待开票
- 已开票
- 已逾期
- 已作废
- 已调整

企业月结账单确认功能属于未来规划。未来企业月结账单需要企业管理员在企业端确认；账单确认前，营运端仍允许调整未关联支付记录的订单费用；账单确认后发现错误时，按作废账单后重新出账处理。

订单完成后发生的追缴、退款、费用调整或账单调整，默认按实际发生月份入账，不回改原订单完成月份或已关闭账期。这样可以保持月度关账稳定；如未来需要支持已开账期重开或追溯调整，需要单独设计账期重开、调整单和审计记录。

订单费用已经有关联支付记录后，不允许直接调整金额。需要调整时，先对原支付记录做全额退款，再重新建立费用并重新收款。未关联支付记录的费用允许按费用管理权限调整，调整时需要保留调整前费用、调整后费用、调整原因、操作人和操作时间。企业月结账单当前实时统计订单金额，因此未支付订单费用调整后，账单统计金额同步变化。

企业月结账单付款当前采用线下公对公转账。企业完成线下转账后，线上填写转账记录或由营运端录入收款记录，用于账单核销、开票和财务追溯。未来需要支持一张账单对应多笔付款记录。

企业月结账单逾期提醒当前尚未实现，属于未来规划。未来逾期提醒不限制企业员工继续使用企业身份下单，提醒对象需要覆盖企业端管理员和营运端财务或账单处理人员。

企业月结订单不进入客户支付、预授权和退款链路，但需要生成企业挂账交易记录。企业挂账交易记录用于订单详情、费用中心、企业账单和后续核对。

个人自付订单和企业非月结订单退款优先原路退回；原路退款失败或业务需要线下退款时，允许具备退款权限的人员登记线下退款，并记录退款渠道、退款凭证、转账单号、操作人和原因。门市租赁退款当前由后台人工处理；24 小时自助租车如产生退款，客户需要联系客服处理，当前不规划 APP 自助退款入口。

当前平台已有基础月度对账单功能，定位为营运商内部月度财务对账单，目前主要统计月度应收、已收和差额。支付渠道对账、发票对账、企业月结自动差异处理等深度对账能力未作为当前完整能力定义。后续如规划更细的财务对账，需要分别定义支付渠道对账、发票对账、企业月结对账的处理端、数据来源、差异处理和操作记录。

### 8.5 公务用车账单

公务用车账单来源不是员工每笔预约订单，而是企业公务用车合约。

公务用车账单依据：

- 公务用车合约
- 合约类型
- 实际用车企业
- 结算代付方
- 可管理车辆配额
- 月缴单车单价
- 年缴单车单价
- 合约有效期
- 续约记录

员工预约公务用车不产生个人支付。

公务用车当前已经包含账单生成和续费处理能力。公务用车账单类型包括新增账单和续费账单：

- 新增账单：企业新增或增加公务用车可用配额时生成，用于本次新增配额的费用确认、汇款和到账核销。
- 续费账单：系统根据既有公务用车合约和续约周期生成，用于企业确认续费车数、续费金额、汇款和合约续期。

公务用车账单状态按以下口径处理：

- 待客户确认：账单生成后，等待企业确认本次新增或续费的车数、金额和账单内容。
- 待提供汇款账户：企业已确认账单，等待营运端财务确认金额并提供本次汇款账户。
- 待汇款：营运端已提供汇款账户，等待企业线下转账。
- 汇款确认中：企业已提交汇款记录、汇款账号后五码或汇款凭证，等待营运端确认到账。
- 已缴费：营运端确认款项到账，账单完成核销。
- 已过期：账单超过有效处理期限仍未完成确认或付款，账单失效。

公务用车账单付款以线下公对公转账为主，线上记录汇款信息和到账确认。账单缴费完成后，根据账单类型执行合约新增配额生效、续约生效或合约有效期延长。

### 8.6 通知中心

平台已有统一通知中心。短信、站内信、APP Push、邮件等通知触达能力按统一通知中心承载，各业务功能触发通知时需要接入统一通知中心，而不是在单个业务模块内各自形成独立通知逻辑。

后续 PRD 涉及订单状态、账单状态、会员方案、企业审核、车辆异常、调度、事故、支付、退款、发票、合约到期、逾期提醒等关键变化时，需要写明是否触发通知、通知对象、通知渠道、触发时点和失败处理口径。

### 8.7 操作记录

平台中的订单、车辆、会员、企业、价格、行销方案、业务规则、账单、权限、服务开关和合约都需要操作记录。当前系统基本已有操作记录，但记录颗粒度需要继续补充。

操作记录至少包含：

- 操作对象
- 操作类型
- 操作人
- 操作时间
- 变更前内容
- 变更后内容
- 操作原因
- 备注

涉及费用、车辆服务类型、企业月结、会员方案、行销方案、历史版本和订单状态的操作，必须记录变更前后值，不能只记录“编辑成功”。

操作记录不允许删除和修改，只能追加新的操作记录。

系统自动动作也必须写入业务操作记录，例如甲租乙还超时未取自动取消、会员方案到期恢复默认方案、企业账单逾期提醒等。自动动作记录需要标明触发规则、触发时间和系统操作来源。

业务操作记录与系统审计日志需要区分。业务操作记录面向营运、客服、门店和企业端可见，用于业务追溯；系统审计日志属于后端运行日志，主要供开发和运维排查系统运行问题。操作记录按角色权限可见，当前不做过度隐藏；具备对应业务查看权限的角色，原则上可以查看其数据范围内的业务操作记录。

新增、修改、停用、恢复、作废、隐藏等业务动作都需要写入业务操作记录。当前不允许物理删除的对象，PRD 中按停用、作废或隐藏处理，并记录对应操作。

### 8.8 权限体系

租户内部权限体系已经存在。营运商可以配置内部角色，并为角色分配菜单权限和操作权限。

典型角色包括门店店员、店长、客服、财务、调度和管理员。后续设计释放操作锁、调整费用、强制切换车辆服务类型、强制解除会员方案、账单调整等高风险动作时，需要落到权限体系中控制，不在业务规则页面单独选择角色。

当前平台对高风险操作采用功能权限控制，暂未上线审批流。费用减免、强制关闭订单、释放操作锁、强制切换车辆服务类型等操作，当前只校验功能权限，不发起上级审批。高风险操作原则上需要记录原因、操作人、操作时间和变更前后内容。

费用调整需要区分普通费用编辑和已结算后的追缴、退款、减免等不同业务阶段，但当前没有按阶段拆分不同权限，统一走订单费用管理相关权限。

门市租赁完成、取消、爽约、拒绝履约、关闭等终态订单产生追缴时，订单主状态不回退，通过独立追缴状态和费用入口处理通知、收款和记录。

订单关闭、取消、爽约、拒绝履约必须选择固定原因。原因由平台固定维护，本期不支持租户后台自定义原因。

操作锁释放按功能权限控制，当前释放时不强制填写原因，也不通知原操作人或门店。

车辆服务类型切换属于调度相关操作，具体可操作角色按租户功能权限配置决定，不在业务规则中固定为某一类角色。

企业账单调整当前走订单费用管理权限，不强制要求财务角色。企业已确认后的调整当前不生成独立调整记录给企业端查看；后续如新增调整单能力，再按调整单规则展示给企业端。

角色按归属范围分为营运角色、车行角色、门市角色和据点角色：

- 营运角色账号属于营运方员工账号，按角色权限查看和操作营运商范围内的数据
- 车行角色账号需要绑定具体车行，默认查看和操作该车行范围内的数据
- 门市角色账号需要绑定具体门市，默认查看和操作该门市范围内的数据
- 据点角色账号需要绑定具体据点，默认查看和操作该据点范围内的数据

车行账号可以登录营运平台。车行账号登录后按绑定车行进行数据隔离，只能查看和操作该车行范围内被授权的数据，例如车辆、门市、据点、订单、调度和报表数据。

门市店员只能查看和处理自己门市的订单。据点角色是否允许处理订单、车辆、整备或车位相关操作，按角色功能权限配置决定；具备对应权限时，仅在绑定据点范围内处理数据。车行类型角色中配置调度权限后，可以查看和处理该车行内跨门市的调度事项；营运类型角色配置调度权限后，可以查看和处理营运商范围内的调度事项。

财务、统计和报表类功能需要支持按车行、门市进行数据隔离和汇总。车辆挂在据点下，车辆资产、库存和使用统计需要从据点上卷到门市，再上卷到车行。

车行账号当前可以查看所属车行范围内的订单详细信息。订单详情可见范围仍受账号绑定车行、角色菜单权限和操作权限控制。手机号、证件信息、证件照片、驾驶证照片、支付记录、发票记录等订单详情信息当前均可见，导出也暂不做隐私脱敏或字段级隐私保护；后续仅在明确提出隐私保护需求时，再单独设计字段级脱敏、查看权限和操作记录。

未来审批流规划为平台通用、可配置能力，不只针对单一场景。费用、订单关闭、车辆调度、强制释放操作锁等高风险动作后续可接入通用审批流。

### 8.9 车行结算与报表

当前车行不参与系统内面向客户的财务结算。客户订单、支付、开票、退款和企业月结账单均以营运商为对外服务主体，营运商与合作车行之间的结算在线下处理。

系统需要保留车行、门市、据点与车辆的归属关系，用于后续统计车辆资产、订单来源、车辆使用、门市营收和车行维度经营情况。

未来车行报表需要支持车行独立营收报表和营运商与车行之间的分账或结算报表。报表指标预留订单数、订单金额、租金、调度费、事故费用、车损费用、车辆使用率、车辆空闲率、取消率等经营指标，并支持按业务线、车行、门市、据点、车辆和时间区间查看。

未来营运商与车行之间需要形成结算单闭环。车行结算单首期按自然月生成，暂不支持按周、半月或自定义周期生成。结算单能力需要覆盖结算周期、结算范围、订单明细、费用明细、调整项、应结金额、结算确认、付款记录和结算状态。结算单需要营运商与车行双方确认，双方确认后作为线下结算和付款依据。该能力当前不影响订单履约、客户付款和企业月结账单。

车行结算的订单归属按实际履约车辆的资产所属车行判断。哪家车行的车产生订单，该订单就进入该车行账务，不按下单门市、取车门市、还车门市、车辆当前停放据点、调度操作人或客户结算方式判断。订单需要保存实际履约车辆的资产所属车行快照，后续车辆资料调整不得反向改变历史订单的车行结算归属。

企业月结订单同样进入车行营收和车行结算。车行结算看车辆资产产生的经营收入，不按客户结算方式排除企业月结订单。

车行结算金额按订单最终应收金额计算，不按实际到账金额计算。客户未付款、企业账单未付款或款项催收失败属于营运方收款风险，不减少车行结算应收。订单最终应收金额按订单结算后的费用明细确定。后续如营运商与车行合同约定坏账共担、风险分摊或结算调整项，需要作为车行结算调整能力单独设计。

车行结算单双方确认后，当前暂不支持重新打开原结算单调整，也暂不支持生成下月调整单。后续如规划车行结算调整能力，再单独设计结算调整规则。

### 8.10 统计报表

当前平台统计功能主要覆盖分时租赁。分时租赁统计已经包含订单统计、会员统计、车辆统计、出租率统计和营收统计。

后续统计报表需要从分时租赁扩展到门市租赁、公务用车和平台整体视角。扩展时需要按业务线、业务模式、营运商、车行、门市、据点、车辆、会员方案、企业和时间区间进行筛选与汇总。

车行、门市、据点角色登录后，只能查看自身数据范围内的统计报表。营运角色按功能权限查看营运商范围内的统计报表。

## 9. 分时租赁业务口径

### 9.1 同站租还

同站租还是分时租赁业务线之一。用户在 APP 中选择同站租还入口，选择据点、车辆、租期、行销方案和增值服务后完成预约。

同站租还核心特点：

- 用户选择具体车辆
- 取车和还车在同一据点
- 标准价区分平日和假日
- 使用预约预授权、还车后扣款机制
- 支持个人自付、企业非月结、企业月结

### 9.2 甲租乙还

甲租乙还是分时租赁业务线之一。用户在 APP 中选择甲租乙还入口，选择取车据点、还车据点、车辆、租期、行销方案和增值服务后完成预约。

甲租乙还核心特点：

- 用户选择具体车辆
- 取车和还车可以是不同据点
- 标准价和行销方案与同站租还分开配置
- 涉及地区与地区之间的调度费用
- 调度费用可以加收，也可以减免
- 预约后订单有效期和短时间取消限制可以按会员方案配置

地区规则：

- 营运商维护地区表
- 据点根据所在位置归属到地区
- 营运商配置地区与地区之间的调度费用
- 从偏远地区还到热门地区时，调度费用可以为减免

甲租乙还调度费按取车营运区域和还车营运区域组成的矩阵配置，不按取还车据点逐一配置。费用规则支持加收或减免，费用类型支持固定金额或按租金比例，并可按租期条件控制适用范围。订单创建和结算时，需要根据订单取车据点、还车据点所属区域命中调度费规则，并将命中的规则版本保存到订单费用快照中。

### 9.3 分时租赁订单主流程

分时租赁典型流程：

1. 用户选择个人身份或企业身份
2. 用户选择同站租还或甲租乙还
3. 用户选择据点、车辆和时间
4. 系统匹配会员方案和行销方案
5. 用户选择增值服务
6. 个人自付或企业非月结订单发起预授权
7. 企业月结订单确认企业月结资格
8. 预约成功
9. 用户在 APP 自助取车
10. 用车中
11. 用户在 APP 自助还车
12. 系统按实际用车情况结算
13. 个人自付或企业非月结订单从预授权扣款
14. 企业月结订单进入企业月结账单
15. 订单完成

### 9.4 分时租赁合作通路租車券

合作通路租車券不是独立业务线，而是分时租赁下可跨同站租还和甲租乙还使用的功能能力。旅行社团体游客租车只是首个落地场景，后续营运商与其他企业合作时可复用该能力。当前一期 PRD 仅实现同站租还，不包含甲租乙还；甲租乙还的批次取还据点、费用、库存和订单校验规则尚未定义，不按已实现处理。合作通路企业作为企业客户的一种合作通路类型存在，用券人仍以个人会员身份使用公开消费者 APP 下单，不作为合作通路企业员工，也不切换企业身份。

合作通路租車券是合作通路企业承担费用、发放给用券人的租车权益凭证。营运端创建租車券批次时支持名单发放和数量生成。名单发放汇入用券人姓名和证件号码，系统按有效名单行逐条生成租車券；证件号码匹配会员已认证身份证或入台证资料时直接发放到账户，未匹配时保留为待发放。数量生成不需要名单，系统按填写数量生成租車券和兑换码，用户在 APP 输入兑换码领取后绑定当前会员账户。

用券人名单导入必须显示导入结果。证件号码格式错误、缺少姓名、缺少证件号码或同一批次证件号码重复属于阻断异常；存在阻断异常时不得确认导入。无异常时显示导入成功，并返回名单行数、已匹配会员行数和待匹配行数。

营运端和企业端可以在批次详情导出租車券列表。租車券列表和导出文件展示用券人完整证件号码，不做脱敏；导出范围按账号数据权限控制，企业端只能导出本企业名下批次。营运端批次详情采用独立页面承载，展示批次基础信息、租車券统计、车辆库存提醒、租車券列表和操作记录。营运端批次详情支持新增租車券，用于名单遗漏、活动临时加名额、现场补发等异常补发场景；新增租車券继承原批次的服务、时间、据点范围和费用归属规则。本期不提供租車券删除或恢复作废；作废属于时间充裕时开发的可选能力，不影响主流程上线。启用 / 停用批次必须填写原因或备注，并写入批次操作记录。

当前一期批次绑定同站租还服务、最早取车时间、最晚还车时间和适用据点范围。APP 传入的预约取车时间必须大于等于最早取车时间且小于最晚还车时间，预约还车时间必须等于最晚还车时间；用券人不能修改服务和最晚还车时间，据点和车辆只能在批次适用范围内选择。订单不向用券人发起个人预授权、个人支付或个人退款，用券人应付金额为 0。同一会员账号使用不同未使用租車券时，可以创建多笔时间重叠的租車券订单，该例外不放宽普通公开租赁订单未完成卡控。

普通散客和租車券用车是否共用据点，由据点类型配置决定。一般预约入口只查询一般预约开放的据点类型；租車券模式按批次适用据点类型和适用据点查询，可以选择一般预约可用或不开放一般预约的据点类型。

营运端新增或编辑租車券批次时，需要按批次整体提供车辆库存提醒。系统先计算适用据点可用车辆，再在当前批次车辆池内计算时间重叠的其他启用批次“最多可能占用”车辆数；预计剩余车辆 = `max(适用据点可用车辆 - 其他批次最多占用, 0)`。当前批次需求大于预计剩余车辆时显示“存在库存风险”，否则显示“未发现库存风险”；信息不完整时显示“待判断”。提醒只作为建批参考，不锁车、不扣减车辆、不阻止保存，也不替代 APP 实时查车结果。

当前一期只实现分时租赁同站租还，不实现甲租乙还租車券。本期不做保留车辆池、车辆预留或排程占用，也不保证每张未使用租車券查询时一定有可预约车辆。APP 按本次预约取车时间、批次最晚还车时间和适用据点范围查询实时可用车辆；无车时提示用券人联系活动方或营运商处理。订单取消后租車券恢复未使用，只要未过期即可重新预约。

租車券车辆查询和订单创建必须执行载具类型校验。后端按所选车辆载具类型与会员可用载具类型判断是否允许预约；不符合时不得创建订单，也不得把租車券标记为已使用。

租車券订单还车后仍按分时租赁原有计费规则计算最终费用。票内覆盖费用、逾时费用、事故、清洁、车损、违章、油电差额等额外费用复用企业月结挂账能力记录到租車券所属合作通路企业名下，不向用券人收款。本期只记录合作通路费用明细和订单费用归属，不做完整合作通路结算单、线上收款和发票闭环。

详细规则见 `02_原型和PRD/PRD/合作通路/合作渠道租车券（同站租还）.md`。

## 10. 门市租赁业务口径

门市租赁包含门市租车和 24 小时自助租车。两者共用车组、价格、行销、增值服务和规则，区别在取还车方式。

### 10.1 门市租车

门市租车是有人服务的门店租车模式。

门市租车核心特点：

- 用户按车组预约
- 后续由系统或门店分配具体车辆
- 店员执行取车验车、资料确认、取车收款、交付车辆
- 店员执行还车验车、费用结算、补缴、退款或企业月结挂账
- 个人自付和企业非月结订单下单时收预授权押金，取车时补足尾款
- 企业月结订单不发起个人支付和预授权
- 履约担保模式下，取车成功后再释放预授权；释放失败不影响订单进入用车中，系统记录释放失败并提示后续人工跟进
- 预授权转租金模式下，取车时预授权扣款失败时保留履约担保模式，门店可改为补收尾款后继续发车；如需继续转租金，必须重新发起扣款并成功

门市租车详细状态、取还车、计费、事故、续租、取消、历史版本和快照规则，见 `01_业务知识库/门市租赁业务说明.md`。

### 10.2 24 小时自助租车

24 小时自助租车是门市租赁下的自助模式。

24 小时自助租车核心特点：

- 用户按车组预约
- 用户在 APP 中自助取车
- 用户在 APP 中自助还车
- 用车过程中的 APP 功能与门市租车一致
- 计费、行销、增值服务、业务规则与门市租车共用
- 与门市租车的主要差异是取还车操作人和操作入口

## 11. 公务用车业务口径

公务用车是企业内部车辆预约管理业务。

公务用车业务流程：

1. 营运商为企业配置公务用车服务
2. 营运商准备企业公务用车据点
3. 营运商设置公务用车月缴或年缴单车单价
4. 营运商建立企业公务用车合约，选择试用或正式合约类型，并设置实际用车企业和结算代付方
5. 合约中设置可管理公务用车配额、有效期和计费周期
6. 企业在企业端建立内部车辆信息
7. 企业将车辆绑定到有效公务用车合约配额
8. 企业按车辆套用清洁保养提醒母版
9. 企业上架车辆给员工预约
10. 员工在公务用车 APP 中预约使用
11. 企业在企业端查看清洁保养提醒并登记已完成
12. 合约到期后，系统强制下架合约内车辆

公务用车预约也有订单或预约状态。公务用车状态用于表达员工预约、用车、取消、完成等过程，但公务用车员工预约不产生个人支付。

公务用车支持按分公司配置预约用车审核。未启用预约用车审核时，员工提交后在车辆、据点、时间窗可用的前提下直接创建有效预约；启用后，员工提交后进入待审核状态，系统推送给员工部门主管审批，分公司管理员也可以在后台审核。开启限时审批后，超过审批时限未处理的预约自动取消，审核状态变为审批超时（过期），车辆时间窗释放给后续预约。

公务用车车辆与租赁车辆当前保持独立管理，暂不支持在公务用车和分时租赁、门市租赁之间互相转换服务类型。

## 12. 历史版本与配置追溯

平台中的价格、行销、规则和服务配置需要支持历史版本。

需要记录版本的配置包括：

- 分时租赁标准价
- 分时租赁行销方案
- 分时租赁增值服务
- 门市租赁标准价
- 门市租赁动态调价
- 门市租赁行销方案
- 门市租赁增值服务
- 租赁业务规则
- 公务用车合约配置
- 智能调度规则

订单详情需要展示订单使用的历史版本。用户点击版本号时，可以查看当时版本的具体配置值。

历史版本详情的展示方式应尽量复用对应配置页面的布局，让用户能够直接对照当前配置和历史配置。

## 13. 原型与 PRD 同步原则

PRD 和 HTML 原型需要保持一致。文档新增状态、字段、规则、历史版本、快照、企业月结、服务开关或业务入口后，已有对应 HTML 原型的模块需要在原型中补充对应入口或示例展示。

原型可以不做深度联动，但必须让开发能够从页面上看到该功能的存在方式。

客服系统、公开 APP、公务用车 APP 等当前没有完整 HTML 原型目录时，需求交付以 PRD 和页面行为说明为主，不为了补齐原型而凭空新建 HTML。后续补齐对应原型目录或明确要求制作原型时，再按同客户端、同模块的既有页面风格补充。

每次修改需求时，需要同步检查：

- 是否影响客服系统授权
- 是否影响租户服务开关
- 是否影响 APP 服务入口
- 是否影响营运平台菜单
- 是否影响企业端展示
- 是否影响个人身份和企业身份
- 是否影响企业月结和非月结
- 是否影响订单状态
- 是否影响车辆、据点、车组和车型
- 是否影响价格、行销、增值服务
- 是否影响订单快照和历史版本
- 是否影响账单

## 14. 平台级 AI 工作流设计方向

RIMO 项目规则已并入统一工作流：

- `jinpeng-workflow`
- RIMO 内置规则：`references/05-RIMO项目规则.md`

该工作流中的 RIMO 项目规则定位为 RIMO 租赁平台产品规划与原型设计助手，不是单纯开发助手。

该规则的职责：

- 读取平台全局业务说明
- 读取分时租赁、门市租赁、公务用车专题业务说明
- 识别任务涉及的客户端
- 识别任务涉及的业务线和业务模式
- 检查个人身份、企业身份、月结和非月结口径
- 检查订单状态、费用流、账单流和车辆流
- 检查价格、行销、增值服务和规则版本
- 检查 PRD 与 HTML 原型是否一致
- 用产品经理口吻编写可直接交付开发的 PRD
- 协助规划未来可扩展到物品租赁平台的通用规则

该 skill 每次处理任务时，必须先判断任务属于：

- 平台级能力
- 分时租赁能力
- 门市租赁能力
- 公务用车能力
- 企业端能力
- 客服系统能力
- 前台 APP 能力
- 跨业务线共用能力

## 15. 后续 AI 协作工作方式

后续 AI 协作 RIMO 平台需求时，应按以下顺序工作：

1. 读取本文
2. 判断任务涉及的业务线和客户端
3. 读取对应 PRD 与 HTML 原型
4. 梳理状态流、资金流、车辆流和账单流
5. 检查会员方案、企业身份、月结和非月结口径
6. 检查价格、行销、增值服务和业务规则
7. 检查是否需要订单快照和历史版本
8. 修改 PRD
9. 修改 HTML 原型
10. 重要业务逻辑或功能调整直接同步到受影响的业务知识库、对应 PRD、原型和文档版本更新记录
11. 输出修改说明和遗留风险

编写 PRD 时使用产品经理口吻。文档内容应可直接交付开发，不写“建议”、“可以考虑”、“待确认”等表达。未进入本期范围的内容，直接写“本期不做”、“本期不支持”、“本期按以下规则处理”。

遇到规则冲突时，优先保持以下原则：

- 客服系统授权控制租户是否拥有业务线能力
- 客服系统取消授权当前只控制营运平台业务线功能权限，当前不会自动隐藏 APP 服务入口
- 租户服务开关当前尚未实现；未来按具体服务模式控制业务是否对用户开放
- 租户停用或冻结后，租户用户不能登录租户后台，历史业务数据继续保留
- 当前前台可按营运商独立 APP 或独立官网入口提供服务；统一 APP 多租户切换已经开始推进，但业务数据仍按租户隔离
- 同一手机号、同一企业在不同租户下完全独立
- APP 只是展示和操作入口，核心业务判断在后端
- APP 下单身份默认个人身份，不用上一次选择作为默认值
- 企业月结不走个人支付链路
- 企业端当前账号类型为总管理员和分公司管理员
- 分时租赁预授权失败直接拒绝订单，门市租赁预授权失败进入待支付
- 门市租赁预授权在取车时已处理，不单独设计取车后预授权到期；分时租赁预授权到期后仍按实际费用生成扣款、补缴或追缴记录
- 企业非月结可被企业端查看，但不进入企业账单
- 企业月结订单需要生成企业挂账交易记录
- 分时租赁基本不走现金退款，同站租还提前还车退积分；门市租赁退款由后台人工处理，24 小时自助退款需要联系客服
- 企业月结发票由人工上传，个人和企业非月结按支付记录自动开票且不支持拆分
- 订单历史信息读取订单快照，不读取当前主数据名称
- 订单费用计算绑定历史规则版本
- 车辆服务类型只能通过调度变更，不能在车辆资料编辑页直接修改
- 分时租赁和门市租赁车辆所在据点变更必须通过调度或位置调整流程处理；公务用车车辆所在据点可由企业端在已配置公务用车据点范围内直接调整
- 车辆当前按服务类型隔离，公务用车与租赁车辆当前不互相转换
- 当前各车行车辆先独立，不做跨车行车辆调拨、跨车行库存池或跨车行车辆借调；门市租赁订单派车、订单改派和改还车门市当前只支持同车行范围
- 车辆档案中的“是否启用”和“车辆营运状态”是独立状态轴；禁用阻断新销售、派车和发车，但不阻断已在履约中的订单完成还车
- 车辆营运状态下，空闲允许即时派车；租用中不参与重叠时间窗派车，但可参与未来无冲突订单预分配；被管控中在解除前不得参与预分配、硬锁和发车
- 门市租赁判断车辆可履约时，必须同时读取是否启用、车辆营运状态、时间窗占用和派车状态/订单状态
- 未来跨业务线车辆共用以统一排程中心为目标，统一排程中心在门市租赁开发完成后再规划和开发，跨业务线优先级当前暂未定义
- 跨业务线共享车辆时，价格和行销仍按订单所属业务线计算
- 已预约车辆后续不可用时，系统不自动取消或自动改派，由营运人员人工处理
- 分时租赁和 24 小时自助租车必须绑定车机后才允许上架预约；车机异常不阻断预约，但会阻断取还车
- 分时租赁和门市租赁的行销方案不跨大类共用
- 订单最终使用一个行销方案；个人身份订单在行销方案后先抵扣积分点数，再抵扣优惠券
- 当前已上线分时租赁企业身份订单仍可按配置使用优惠券和积分点数；未来规划和门市租赁新增规划口径为企业身份订单不支持优惠券和积分点数
- 当前高风险操作只做功能权限控制，审批流是未来通用可配置能力
- 平台有统一通知中心，关键业务状态变化需要写明通知对象、渠道和触发时点
- 业务操作记录不允许删除，系统自动动作也需要写入业务操作记录
- 新增、修改、停用、恢复、作废、隐藏等业务动作都需要写入业务操作记录
- 系统审计日志是后端运行日志，不等同于业务操作记录
- 公务用车员工预约不产生个人支付

后续 AI 审查需求时，输出结构固定为：

1. 结论
2. 发现的逻辑漏洞
3. 需要同步修改的 PRD
4. 需要同步修改的 HTML 原型
5. 需要同步到业务知识库、PRD、原型或版本更新记录的内容
6. 暂未定义的问题
