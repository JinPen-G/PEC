本文用于让后续协作门市租车业务线的产品、设计、开发或 AI，能够快速理解当前门市租车订单、计费、规则、派车、原型与 PRD 的整体口径。

后续继续补充或修改门市租车功能时，需要先阅读本文，再对照对应 PRD 与 HTML 原型文件，保证订单状态、资金流、规则快照、历史版本、企业月结、派车逻辑与页面展示保持一致。

本文不是替代各功能 PRD，而是门市租车业务的全局上下文说明。具体字段、页面交互和细节规则，以各模块 PRD 与 HTML 原型为准；当本文与细节 PRD 不一致时，需要同步修正文档口径。

## 3. 业务定位

门市租车是以门店为核心的租车业务。用户可以通过门店、客服或后台人员完成预约下单，订单按车组进行预约，实际车辆在后续派车环节完成预分配或硬锁定。

门市租车订单不是分时租赁订单，也不是代步车订单。门市租车订单的核心链路包括：

1. 新建订单
2. 收取预授权押金或企业月结确认
3. 车辆预分配
4. 取车验车
5. 取车收款或确认企业月结
6. 用车中
7. 续租、事故、改还车门店等中途事件
8. 还车验车
9. 结算
10. 支付、退款、挂账或完成

门市租赁当前以车组库存和订单时间段作为预约基础。门市租车和 24 小时自助租车订单创建后先锁定车组库存，不等同于立即锁定具体车辆。具体车辆由智能调度或人工派车在后续阶段处理；后续完成硬锁车辆后，用户端或后台才展示可交付车牌。

### 3.1 门市与据点口径

平台当前站点层级为车行 -> 门市 -> 据点。门市是客户服务和门店人员作业的层级，据点是具体停车场、停车区域、自助取还车点或车辆实际停放位置。

车行、门市和据点分别使用独立管理页面。车行维护车辆资产归属、同车行调度和经营归集范围；门市维护客户服务组织、营业时间和店员履约信息；据点维护实体停车位置、地址、坐标、车位和服务能力。据点页面左侧车行 / 门市树只用于筛选，不承担车行或门市新增、编辑。

车行账号只查看和维护当前车行范围；不能新增车行，可在具备权限时新增本车行门市。门市账号只查看和维护当前门市，不能新增门市或查看同车行其他门市。只读、新增、编辑、启停和导出分别受功能权限控制，后端必须同时校验数据范围。门市创建后所属车行不得变更。

父级停用不改写下级对象状态。车行或门市停用后，相关门市、据点和能力原状态保留，但不得接受新预约、新订单、新上架或新派车；已创建订单继续按原订单处理。重新启用父级后，下级对象按自身状态恢复参与业务。

门市租车可用条件为：车行启用、门市启用、门市租车状态启用，并且门市下至少存在一个已启用且具备门市租车能力的据点。24 小时自助租车可用条件为：车行启用、门市启用、具体据点启用且该据点 24 小时自助租车能力启用；24 小时自助租车不依赖门市租车状态。

门市租赁下需要区分门市租车和 24 小时自助租车：

- 门市租车是店员服务模式。客户下单时选择取车门市和还车门市，不直接选择停车场据点。车辆仍然挂在门市下的具体据点，系统按门市下具备门市租车服务能力的可用据点汇总车组库存和可派车辆。
- 门市租车派车后，订单列表和订单详情需要展示车辆当前所在据点，展示位置放在取还站点信息中。详情页展示格式为“门市 - 据点 - 地址”，列表无地址时展示为“门市 - 据点”。门店人员根据该据点信息到车辆实际所在据点备车，并将车辆交付到门市交付区或指定交接点。车辆所在据点由已派车辆带出，不由店员手动选择。取车记录需要保存取车门市、车辆所在据点、交付位置、车辆和操作人。
- 门市租车还车时，客户归还给还车门市。门店人员完成验车后，再记录车辆最终停放的归还据点、楼层、车位和照片。
- 24 小时自助租车是用户自助模式。用户需要看到具体取还车据点、地址、车位指引和自助取还车条件，因此 24 小时自助租车的客户取还车点必须落到具体据点。
- 24 小时自助租车允许还到同门市下其他自助据点。可还车据点只能开放已配置为允许还车且具备自助服务能力的据点，不允许用户还到门市下任意未开放据点；同门市下不同自助据点还车不产生调度费。

## 4. 客户与支付口径

### 4.1 个人自付订单

个人会员订单由客户本人支付费用。下单时按租赁业务规则收取预授权押金，预授权金额可为固定额度或租金比例；租金比例本期不超过 100%。本期不做全额支付场景。

个人自付订单涉及：

- 下单预授权押金
- 取车补足租金尾款
- 取车时选择预授权处理方式
- 还车结算后的补缴或退款
- 取消、爽约、事故、追缴等费用处理

下单预授权押金本期统一走线上预授权，不支持现金押金、线下押金或仅登记线下凭证。取车尾款、还车补缴、追缴等实际收款可按支付配置走线上或线下收款。

### 4.2 企业非月结订单

企业非月结订单与个人自付订单的支付链路一致。客户可以使用企业资格、企业协议价或企业可用行销方案完成计费，但费用仍由下单人自行支付。后续客户是否向企业报销，不在系统内处理。

企业身份订单不支持优惠券和积分。非月结企业订单只使用企业资格可用行销方案，费用仍由下单人自行支付。

企业非月结订单涉及：

- 下单预授权押金
- 取车补足租金尾款
- 还车补缴或退款
- 取消、爽约、事故等费用由下单人支付

### 4.3 企业月结订单

企业月结订单不对客户发起支付、预授权、尾款补缴、退款等动作。订单产生的租金、服务费、续租费、异地还车费、事故费、取消费、爽约费、追缴费等，统一进入企业月结账单。

企业月结订单当前不做企业额度控制。本期不需要处理额度占用、额度不足、额度释放等逻辑。

企业月结订单的费用处理口径：

- 下单时不收预授权押金
- 取车时不收尾款
- 还车结算时不进入待补缴或待退款
- 还车应收金额确认后挂账到企业月结账单
- 月结订单不区分企业协议内费用和个人承担费用
- 月结订单所有费用统一归入企业账单
- 完成后产生的事故追缴或补充费用，也作为企业月结账单费用处理

## 5. 订单状态总览

### 5.1 主状态

门市租车订单主状态用于表达订单所处的业务阶段。列表、详情、筛选、统计、工作台提醒均应使用同一套状态口径。

| 状态    | 含义                                         |
| ----- | ------------------------------------------ |
| 待支付   | 个人自付或企业非月结订单创建后，客户尚未完成下单预授权押金；企业月结订单不进入该状态 |
| 已预约   | 订单已生效，车组库存已占用，等待取车                         |
| 取车超时  | 已超过预约取车时间，订单仍未开始取车或未完成取车                   |
| 验车中   | 门店已点击取车并进入取车操作流程，正在进行取车验车、资料确认、取车收款等操作     |
| 用车中   | 取车流程已完成，车辆已交付客户使用                          |
| 续租中   | 客户正在发起或处理续租申请                              |
| 还车超时  | 已超过预约还车时间，订单仍未完成还车                         |
| 事故处理中 | 订单存在事故处理事项，需根据事故阶段与费用结果继续处理                |
| 待结算   | 门店已提交还车验车，车辆已归还，订单进入费用核算                   |
| 待补缴   | 个人自付或企业非月结订单还车结算后存在客户需补缴金额                 |
| 待退款   | 个人自付或企业非月结订单还车结算后存在需退还客户金额                 |
| 已完成   | 订单主流程完成，费用已结清或已完成企业月结挂账                    |
| 已取消   | 订单在取车前取消                                   |
| 已爽约   | 订单超过取车保留时间后仍未取车，按爽约处理                      |
| 已拒单   | 门店或系统在订单生效前拒绝订单                            |
| 已关闭   | 订单因异常原因关闭，不再继续履约                           |

### 5.2 子状态与标签

主状态只表达订单主流程阶段。以下信息使用子状态、标签或独立字段表达，不单独扩展主状态：

- 支付状态
- 预授权状态
- 取车操作锁状态
- 派车状态
- 续租状态
- 事故状态
- 还车结算状态
- 企业月结状态
- 退款状态
- 完成后追缴状态

列表页可以在主状态旁展示标签，例如：`预分配`、`已硬锁`、`取车操作中`、`企业月结`、`待退款`、`完成后追缴`。

### 5.3 订单状态、派车状态与车辆状态关系

门市租赁开发时，必须将以下四条状态轴线分开判断，不能合并为同一个“订单状态”或“车辆状态”字段处理：

| 状态轴线   | 典型字段                                                                       | 作用                        |
| ------ | -------------------------------------------------------------------------- | ------------------------- |
| 订单主状态  | `pending_payment`、`reserved`、`inspecting`、`renting`、`settlement_pending` 等 | 表达订单当前业务阶段。               |
| 派车状态   | `pending`、`pre_assigned`、`locked`、`manual_reassigned`、`upgraded`           | 表达订单与具体车辆的绑定关系。           |
| 车辆启用状态 | `enabled`、`disabled`                                                       | 控制车辆是否允许参与新订单销售、派车、硬锁和发车。 |
| 车辆营运状态 | `idle`、`renting`、`controlled`                                              | 表达车辆当前是否空闲、正在履约或处于内部管控。   |

处理口径如下：

- 订单主状态不因为车辆被禁用或进入被管控中而直接跳转到异常终态。
- 已预约订单的已派车辆在取车前变为 `disabled` 或 `controlled` 时，系统先做车辆复核和重派；重派失败时，将订单标记为需要人工调度，不自动取消订单。
- `disabled` 只阻断新销售、派车、硬锁和发车，不阻断已经开始履约的订单完成还车。
- `renting` 表达车辆当前时点正在被上一笔订单占用，不代表该车辆不能参与未来无冲突订单的排程。
- `controlled` 表达车辆处于清洁、保养、调度、还车待整备等内部处理阶段，管控未解除前不得参与新的派车和发车。

## 6. 下单与预约规则

### 6.1 订单创建

下单时按取车门市、还车门市、车组、租期、客户类型、企业资格、行销方案、服务产品等信息生成订单。个人订单可使用优惠券和积分；企业身份订单不支持优惠券和积分。

订单创建时需要保存订单快照。所有与订单核对相关的名称、展示字段、配置版本和值，均应独立保存到订单侧，不能只保存基础资料 ID。

订单需要保存的典型快照包括：

- 下单门店、取车门市、还车门市名称
- 门市下参与库存计算的服务据点范围
- 客户姓名、手机号、证件展示信息
- 企业名称、企业资格、月结标识
- 车组名称、车型展示信息
- 车辆信息、车牌号、车辆识别信息
- 行销方案名称、优惠内容、版本号
- 个人订单的优惠券、积分抵扣信息
- 基础产品定价版本号
- 动态调价策略版本号
- 业务规则版本号
- 服务产品版本号
- 里程规则、油电规则、押金规则、取消规则、爽约规则

后续基础资料改名、车组改名、门店改名、企业名称调整、价格规则调整时，不得影响历史订单展示和核对。

### 6.2 待支付

个人自付与企业非月结订单创建后进入待支付。待支付状态只保留车组库存，不进行具体车辆派车，不进入智能调度硬锁定。

待支付订单需要在规则配置的支付保留时间内完成下单线上预授权押金。超时未支付时，订单按规则自动关闭或释放库存。

企业月结订单不进入待支付。企业月结订单确认企业月结资格后直接进入已预约。

### 6.3 已预约

订单完成下单预授权押金，或企业月结订单确认月结后，进入已预约。

已预约订单已占用车组库存，可以进入智能派车、车辆预分配、取车提醒等后续流程。

门市租车订单创建时锁定的是取车门市下可服务据点汇总后的车组库存，不锁定客户可见的具体据点。24 小时自助租车订单创建时需要锁定具体取车据点下的车组库存，并按还车规则锁定对应还车据点或允许还车据点范围。

车组库存按“时间窗 + 服务范围 + 车组”实时计算。门市租车按取车门市下具备门市租车能力的据点汇总可服务车辆数；24 小时自助租车按用户选择的具体取车据点计算可服务车辆数。可售库存等于可服务车辆数减去同时间窗有效订单占用数和内部不可售任务占用数。每笔有效门市租赁订单固定占用 1 个车组库存名额，派车状态只表达该订单是否已经绑定具体车辆，不额外重复扣减库存。

库存占用时间窗按订单取车时间、还车时间和订单间隔时间计算：

```text
目标占用时间窗 = 取车时间 - 订单间隔时间 至 还车时间 + 订单间隔时间
```

以下订单继续占用车组库存：`pending_payment` 保留期内订单、`reserved`、`pickup_overdue`、`inspecting`、`renting`、`renewing`、`overdue`、`accident_processing`。`pre_assigned`、`locked`、`manual_reassigned`、`upgraded` 只改变具体车辆绑定，不重复增加车组库存占用。

还车验车提交后，订单不再作为车组库存占用，但车辆进入还车待整备或内部处理，在订单完成还车确认且车辆恢复 `enabled + idle` 前，不得重新计入可服务车辆数。`completed`、`cancelled`、`no_show`、`rejected`、`closed` 确认后释放车组库存和具体车辆绑定；终态后追缴不再占用库存。

创建订单、补收待支付预授权、续租、改租期、改车组、改派和硬锁时，后端必须重新执行库存和时间窗校验，并在同一事务内完成库存占用、释放或更新，不得仅以前端库存查询结果作为提交依据。

门市租赁待支付或已预约阶段的资源保留时长按固定系统规则处理，当前不做租户可配置。甲租乙还的预约后订单有效期仍按会员方案或租户规则配置处理，不与门市租赁资源保留规则混用。

## 7. 取车规则

### 7.1 进入验车中

门店人员点击订单的取车操作后，订单立即进入验车中，并生成取车操作锁。

进入验车中代表门店已经开始处理取车流程，但不代表车辆已交付客户。验车中期间需要完成：

- 客户身份核对
- 驾照、证件、授权资料确认
- 车辆外观与设备验车
- 取车照片或附件上传
- 取车费用确认
- 个人自付或企业非月结订单补足尾款
- 企业月结订单确认月结挂账
- 车辆所在据点查看和交付位置确认
- 车辆交付确认

### 7.2 验车中关闭窗口或中断操作

门店人员点击取车后，如果关闭取车窗口、浏览器中断、页面刷新或未继续操作，订单保持验车中状态，取车操作锁保持占用。

系统需要记录取车操作开始时间、操作人、操作门店和操作锁。超过配置的操作锁超时时间仍未完成取车时，订单展示为取车操作中断或操作超时。

有权限的人员可以释放取车操作锁。释放后，订单回到取车前状态，并重新判断当前时间：

- 未超过预约取车时间，回到已预约
- 已超过预约取车时间但未超过取车保留时间，进入取车超时
- 已超过取车保留时间，进入已爽约

释放操作锁的权限由角色权限配置控制，不在租赁业务规则页面选择角色。

### 7.3 取车前车辆状态校验

门店确认发车前，系统必须同时校验以下条件：

| 校验项    | 通过条件                      | 不通过时处理口径                     |
| ------ | ------------------------- | ---------------------------- |
| 车辆启用状态 | 车辆为 `enabled`             | 阻断发车；若订单尚未开始履约，重新校验是否可同车行改派。 |
| 车辆营运状态 | 车辆为 `idle`，且不存在内部管控       | 阻断发车；`controlled` 车辆不得发车。    |
| 派车状态   | 当前订单已存在 `locked` 车辆       | 未硬锁时不允许发车。                   |
| 时间窗占用  | 前序订单、订单间隔和内部任务不与当前取车冲突    | 冲突时解除原绑定并尝试重派；失败进入人工调度。      |
| 服务匹配   | 车辆服务类型、车组、取车门市可交付范围满足订单要求 | 不满足时不允许发车。                   |

已硬锁车辆在取车前变为 `disabled` 或进入 `controlled` 时，订单主状态保持不变。系统应先在同车行范围内重新复核和改派；改派失败时，订单进入人工调度处理，门店不得直接确认发车。

### 7.4 取车收款

个人自付与企业非月结订单在取车时需要补足租金尾款。下单阶段只收取预授权押金，本期不做全额支付。

取车时支持两种预授权处理模式：

| 模式     | 处理方式                                   |
| ------ | -------------------------------------- |
| 履约担保   | 下单预授权作为履约担保，取车时客户另行支付租金尾款；车辆交付后释放预授权押金 |
| 预授权转租金 | 将下单预授权押金转为租金支付的一部分，用于抵扣取车应付尾款          |

门市租赁预授权在取车时已经完成释放、转租金或履约担保处理，不单独设计取车后的预授权到期处理。

企业月结订单取车时不发起支付，不发起预授权处理，不存在释放或转租金动作。取车确认后，租金后续进入企业月结账单。

### 7.5 进入用车中

取车验车完成、资料确认完成、个人自付或企业非月结订单取车应收完成、企业月结订单月结确认完成、门店确认交付车辆后，订单进入用车中。

用车中代表车辆已交付客户，订单开始进入实际履约阶段。

进入用车中时，取车记录需要保存取车门市、车辆所在据点、交付位置、实际车辆、车牌、里程、油量或电量、照片、操作人和操作时间。车辆所在据点取确认发车时已派车辆的当前所在据点，后续门市、据点或车辆资料调整，不改写该取车快照。

24 小时自助租车在取车时，发车里程、发车油量或电量默认读取车机最新实时值，页面展示同步时间并允许后台人员按现场核对结果人工修正。确认发车后，以最终确认值写入取车记录和取车展示快照；车机值只作为默认带入来源，不单独覆盖人工确认结果。

24 小时自助取车必须闭合支付或月结确认、取车记录、车机开锁和订单状态。个人自付和企业非月结订单在自助取车前必须结清整笔订单应收金额；下单阶段的预授权冻结不等同于租金支付，未转租金时不得抵扣订单总额。整单未结清时，系统不得下发车机开锁指令。车机开锁成功前，订单不得进入用车中，用户 APP 控车权限不得生效。支付、预授权转租金或月结确认已经成功但开锁失败时，系统保留已成功资金或月结记录，不重复收款、扣款或挂账；订单通过自助取车状态和自助异常标记进入重试或人工处理。

确认发车后，车辆营运状态更新为 `renting`，车辆启用状态保持原值不变。

## 8. 还车与结算规则

### 8.1 进入待结算

门店人员提交还车验车后，订单进入待结算。进入待结算代表车辆已经归还，门店开始核算最终费用。

还车验车需要记录：

- 实际还车时间
- 订单当前还车门市
- 车辆最终停放据点、楼层、车位和照片
- 还车里程
- 油量或电量
- 车辆外观与设备情况
- 新增损伤
- 附件、照片、备注
- 服务产品消耗情况
- 需要人工确认的费用项

24 小时自助租车在还车时，还车里程、还车油量或电量默认读取车机最新实时值，页面展示同步时间并允许后台人员按现场核对结果人工修正。提交验车后，以最终确认值写入还车验车记录和还车结算快照；车机值只作为默认带入来源，不单独覆盖人工确认结果。

24 小时自助还车必须闭合还车记录、费用结算、补缴或退款、企业月结挂账、车机落锁、控车权限回收和订单完成状态。用户提交还车记录后，系统先计算最终补/退租金；个人自付和企业非月结订单完成补缴、退款受理或账单平衡记录后，企业月结订单完成月结挂账后，才允许下发车机落锁指令。车机落锁成功或人工确认车辆已锁闭前，订单不得进入已完成。补缴成功、退款受理或月结挂账成功但落锁失败时，系统保留已成功资金或月结记录，不重复收款、退款或挂账；订单通过自助还车状态和自助异常标记进入重试或人工处理。

门市租车还车时，客户面向的是订单当前还车门市。订单只能由订单当前还车门市办理还车，其他门市默认没有该订单的还车操作入口。门店完成验车后，需要记录车辆最终停放到门市下哪个据点。订单当前还车门市用于判断是否异地还车，最终停放据点用于车辆资产位置、后续整备和再次派车。同一还车门市下不同归还据点不触发异地还车费或调度费。

服务站点管理列表中的车位概况只用于门店查看合作停车场当前是否还有空位，不作为门市租车是否可还车的前置拦截条件。甲租乙还车位与站点分布查看沿用既有独立功能，不在该列表重复展示。

若订单关联的取车门市、还车门市、取车据点或还车据点在订单创建后被关闭或暂停，后台和 APP 只展示据点状态与提示文案，不自动改站、不自动转单、不自动取消。关闭提示文案统一为“据点已关闭，请联系客服处理”；暂停提示文案统一为“据点已暂停，请联系客服处理”。本期由客服或门店人工联系客户并处理后续改还车门市、改还车据点或关闭订单。

客户或门店需要调整还车门市时，必须先执行“改还车门市/转单”。转单完成后，订单当前还车门市更新为新门市，新门市获得订单列表、订单详情和还车操作权限。转单允许状态为 `reserved`、`pickup_overdue`、`inspecting`、`renting`、`renewing`、`overdue`、`accident_processing`；进入 `settlement_pending`、`payment_due`、`refund_pending` 或终态后不允许转单。

改还车门市的固定原因包括：客户要求改还车门市、门店协商改还车门市、车辆回流安排、原还车门市无法接收、事故/异常处理需要、其他。选择“其他”时必须填写备注。

改还车门市/转单本期仅支持同车行范围内处理。目标还车门市必须与订单取车门市或车辆资产所属车行处于同一车行组织范围内；跨车行转单本期不支持，遇到跨车行还车需求时按线下协商处理，不在系统内直接转单。

转单费用按“新异地还车费 - 旧异地还车费”计算差额。旧异地还车费按取车门市到原订单当前还车门市计算，新异地还车费按取车门市到新订单当前还车门市计算。客户自付订单差额进入取车尾款或还车结算，企业月结订单差额进入企业月结账单。

改还车门市确认前，系统必须检查当前车辆在原订单当前还车门市是否已经有后续预约、待取车或硬锁订单。存在后续预约冲突时，转单弹窗展示冲突订单号、取车时间、客户、原还车门市、当前车辆和派车状态，并提供“快捷改派后续订单”。冲突未处理前不能确认转单；快捷改派成功后释放原车辆在原还车门市的后续占用，再允许完成转单。

转单完成后，新门市获得订单列表、订单详情和还车操作权限；原门市仅保留查看，不再具备还车、转单、改派等操作权限。

24 小时自助租车订单需要支持“改还车据点”。改还车据点用于把订单当前还车据点调整到具体自助据点，适用于原还车据点关闭、暂停、临时不可用或客服人工协商变更场景。若只在同一还车门市下调整据点，不产生异地还车费或调度费；若改到其他还车门市下的据点，则先更新订单当前还车门市，再按门市口径计算异地还车费差额并校验后续预约冲突。门市租车改还车门市和 24 小时自助租车改还车据点当前均由后台处理，APP 自助申请入口当前不做，也暂无规划。

### 8.2 还车后的车辆状态回写

还车流程完成后，车辆状态回写需要与订单状态分开处理：

- 还车验车提交后，车辆结束用车中占用并进入内部处理阶段。在订单仍处于 `settlement_pending`、`payment_due`、`refund_pending` 时，车辆不得重新进入新的派车候选池。
- 订单确认还车后，如车辆仍为 `enabled` 且无需清洁、保养、调度或其他内部处理，车辆营运状态回写为 `idle`。
- 订单确认还车后，如车辆仍需清洁、保养、调度、还车待整备或其他内部处理，车辆营运状态回写为 `controlled`。
- 车辆在还车完成时若已 `disabled`，则继续保持禁用，不恢复新订单派车资格。

### 8.3 还车结算费用

还车结算不重复收取已在取车阶段收取的租金。还车结算只核算订单最终应收与已收、已授权、已挂账之间的差额。

还车结算可能涉及：

- 超时还车费用
- 提前还车调整
- 续租费用
- 甲租乙还费用
- 超里程费用
- 油量或电量差额费用
- 服务产品差额
- 车辆损伤费用
- 事故费用
- 人工加收费用
- 人工减免费用

### 8.4 待补缴、待退款与完成

个人自付与企业非月结订单结算后按差额进入不同状态：

- 差额大于 0：进入待补缴
- 差额小于 0：进入待退款
- 差额等于 0：确认后进入已完成

待补缴订单完成补缴后进入已完成。

待退款订单完成退款或确认退款处理完成后进入已完成。

门市租赁退款当前由后台人工处理。24 小时自助租车如产生退款，客户需要联系客服处理，当前不规划 APP 自助退款入口。

企业月结订单还车结算确认后直接进入已完成，应收金额进入企业月结账单。企业月结订单不进入待补缴或待退款。

## 9. 续租规则

续租适用于用车中、续租中、还车超时等仍处于履约阶段的订单。

续租需要校验车辆后续是否存在冲突订单。本期不设置最大延长天数限制，只要没有订单冲突，即可按规则发起续租。

个人自付与企业非月结订单续租时，可以按规则要求立即支付续租费用，或将部分费用并入还车结算。具体处理方式以续租 PRD 和业务规则配置为准。

企业月结订单的续租费用统一进入企业月结账单，不发起客户支付。

续租生成后，需要记录续租快照，包括续租前后还车时间、续租费用、价格版本、规则版本、操作人、操作时间和支付或挂账结果。

## 10. 甲租乙还规则

甲租乙还是指取车门市与还车门市不同。

订单创建时如果已选择异地还车，则费用应在下单或取车费用中体现。

用车中申请变更还车门市时，需要判断新还车门市是否支持接收、费用是否变化、车辆是否可回收、后续排程是否受影响。

个人自付与企业非月结订单的甲租乙还差额，可以按规则立即支付或进入还车结算。

企业月结订单的甲租乙还费用统一进入企业月结账单。

## 11. 取消、关闭与爽约

### 11.1 取消

订单在取车前可以按规则取消。取消费用支持固定金额、按预授权比例和阶梯扣费。

阶梯扣费的数值根据选择的扣费类型配置：

- 选择固定金额时，阶梯值为固定金额
- 选择按预授权比例时，阶梯值为预授权比例

个人自付与企业非月结订单取消后，根据已收、应扣、应退金额进行退款或扣费。

企业月结订单取消产生的费用进入企业月结账单。

### 11.2 爽约

订单超过预约取车时间后进入取车超时。超过取车保留时间后仍未取车，进入已爽约。

爽约费用按租赁业务规则配置执行。个人自付与企业非月结订单从预授权或已支付费用中扣取；企业月结订单进入企业月结账单。

### 11.3 关闭

关闭用于处理异常订单。关闭通常表示订单不再继续履约，并且不按正常取消或爽约计费。

关闭场景需要记录关闭原因、操作人、操作时间、费用处理结果和备注。涉及个人自付退款时，需要形成退款记录；涉及企业月结时，需要按关闭结果决定是否产生企业账单费用。

## 12. 事故与完成后追缴

事故可以发生在用车中、还车结算中，也可以在订单完成后补录。

用车中发生事故时，订单可以进入事故处理中。事故处理完成后，根据车辆是否继续履约、是否换车、是否提前结束、是否产生费用，回到对应业务状态。

还车时发现事故或损伤时，事故费用进入还车结算。

订单进入终态后补录事故费用、违章、ETC、停车费、后发现车损或其他有责费用时，不改变订单主状态。`completed`、`cancelled`、`no_show`、`rejected`、`closed` 都保持原终态，通过追缴状态、事故状态或费用追缴记录表达后续处理。

个人自付与企业非月结订单的完成后追缴需要形成客户应付记录，并允许客户在线支付。企业月结订单的完成后追缴直接挂入企业月结账单。

## 13. 计费规则

### 13.1 标准价

基础产品定价按车组配置标准价。标准价不区分平日和假日。

标准价是行销方案打折和门市租车基础租金计算的基础。

### 13.2 行销方案

行销方案在标准价基础上进行优惠。行销方案可以配置平日和假日不同的优惠价或折扣价。

个人资格预约和企业资格预约可以匹配不同可用行销方案。原型中只需要通过示例数据表达该逻辑，不要求做深度联动。

有可用行销方案时，APP、官网或后台下单页展示所有可用方案给用户或操作人选择，默认选中最终价格最低的方案。订单最终使用一个行销方案，不自动叠加多个行销方案。

门市租车取车时需要现场复核证件和资质。行销方案仍先按基础适用条件匹配，会员方案、企业资格、适用门市、适用车组、有效期等由系统判断；到店人工核验只是行销方案的可选补充项。学生、教师、军警、医护、长者等需要看证明文件的优惠资格，可以在方案中开启到店人工核验，由店员在取车时人工核验并上传证明文件。

用户下单时可以选择开启到店人工核验的行销方案，订单快照保存方案版本、是否需要到店核验、资格名称和证明文件说明。证明文件说明由行销方案配置人员填写文本，用于提示门店大致需要查看哪些证件或证明；取车时不固定附件名称，门店核验通过至少上传 1 个证明文件附件，最多上传 3 个证明文件附件。取车时核验通过，原方案继续生效；核验不通过或客户无法提供有效证明文件，原方案不得继续生效，店员必须在取车流程内更换为客户当场符合资格的行销方案，或改为不使用优惠。更换行销方案属于商业条件变化，需要生成取车事件级增量快照，并按取车时命中的方案版本重新试算尾款，不覆盖原订单级基线快照。

需要到店人工核验的行销方案本期仅适用于有人服务的门市租车。24 小时自助租车没有店员现场核验能力，本期不开放选择该类方案。

### 13.3 优惠券与积分

门市租赁支持优惠券和积分抵扣。优惠券可以配置适用服务范围，类型包括租金折扣、租金现金减免、租用时数减免和折抵里程。

积分有有效期限，来源包括注册、邀请、同站租还提前还车积分退回、活动和营运人员发放。

个人身份订单费用抵扣顺序为标准租金、行销方案、积分、优惠券。最终订单金额不得小于 0。

企业身份订单按未来规划口径处理，不支持优惠券和积分点数。企业身份订单只使用企业会员方案匹配到的行销方案，不展示优惠券和积分抵扣入口。

### 13.4 租期计费

门市租车起租按 24 小时计算。

超过完整 24 小时后的剩余用车时长，按以下规则计算：

- 不足 1 小时按 1 小时计
- 每超过 1 小时按牌价的 10% 计费
- 从第 5 小时起按 1 天计费

跨平日、假日时，按每一轮 24 小时周期的起始时间判断该周期适用平日价或假日价。剩余小时段以新一轮 24 小时的起始时间判断平假日。

提前还车是否产生可退金额按租赁业务规则判断。可退时，个人自付和企业非月结订单进入后台人工退款或还车结算抵扣；企业月结订单按企业账单调减处理。

### 13.5 动态调价

动态调价策略用于调整门市租车牌价或费率。订单计算时需要记录动态调价策略版本。

订单详情需要展示订单使用的标准价版本、动态调价版本、行销方案版本和业务规则版本，并支持点击版本查看当时版本的具体配置值。

## 14. 规则版本与订单快照

### 14.1 版本记录

以下配置需要有版本记录：

- 基础产品定价
- 动态调价策略
- 行销方案
- 租赁业务规则
- 服务产品
- 里程规则
- 押金规则
- 取消规则
- 爽约规则
- 智能调度规则

每次启用新配置时生成新版本。历史订单继续绑定下单时、续租时、还车时或事件发生时的版本，不随当前配置变化。

门市租赁统一采用“订单级基线快照 + 事件级增量快照”模型。下单时固化原订单商业快照作为合同基线；后续仅涉及履约分配、不改变用户商业承诺的动作继续读取订单级基线快照；涉及租期、车组、行销方案、价格规则、税费口径等商业条件变化的事件，必须生成事件级增量快照，并按事件发生时命中的版本结算差额，不覆盖原订单基线快照。

老订单保护保护的是原订单基线快照，不是保护后续商业事件永久沿用下单时版本。既有订单未发生商业条件变化时，继续按原订单基线快照执行；既有订单后续如发生续租、改租期、改车组、取车现场改行销方案、逾时重计费等需要重定价的商业事件，则按事件发生时命中的有效版本生成事件级增量快照，仅结算该事件影响的增量差额。

#### 快照适用矩阵

| 场景                          | 是否生成新快照 | 快照类型    | 结算口径                                             |
|:--------------------------- |:------- |:------- |:------------------------------------------------ |
| 新建订单                        | 是       | 订单级基线快照 | 保存下单时命中的标准价、动态调价、行销方案、业务规则、税费和会员资格等商业条件。         |
| 派车、硬锁、同车组改派、同车组换车、换据点、备车、验车 | 否       | 不生成     | 继续读取订单级基线快照，不触发重定价。                              |
| 续租                          | 是       | 事件级增量快照 | 仅对新增租期部分按事件发生时命中的版本计价并结算差额。                      |
| 改租期                         | 是       | 事件级增量快照 | 仅对变更部分按事件发生时命中的版本重算差额，不回改原基线部分。                  |
| 改车组                         | 是       | 事件级增量快照 | 按变更后车组及事件发生时命中的价格、规则和方案重算差额。                     |
| 改派导致改车组、升等或降等               | 是       | 事件级增量快照 | 需要保存原车组、目标车组、差价和差价处理方式；即使最终免费升等、差额为 0，也需要保留事件快照。 |
| 取车现场改行销方案                   | 是       | 事件级增量快照 | 按取车时命中的方案版本重新试算差额，保留原订单基线方案快照。                   |
| 改还车门市或改还车据点且产生异地还车费/调度费差额   | 是       | 事件级增量快照 | 仅对变更后的异地还车费或调度费差额生成事件快照；同门市内仅换据点且无费用差额时不生成。      |
| 正常还车且无新的商业条件变化              | 否       | 不生成     | 按订单级基线快照及既有事件快照链结算，不读取当前主数据。                     |
| 逾时还车或还车时触发重计费               | 是       | 事件级增量快照 | 仅对超出原约定部分按还车事件时命中的有效版本结算差额。                      |

事件级快照至少需要保存以下内容：

1. `eventSnapshotId`
2. `eventType`
3. `snapshotTime`
4. `baseSnapshotId`
5. 触发节点（取车、改单、续租、还车、客服处理等）
6. 命中的价格、行销方案、业务规则、服务价格版本
7. 商业条件变更前后值
8. 差额金额与差价处理方式
9. 结算去向（取车补收、还车补缴、还车退款、企业月结挂账、不调整费用）
10. 操作人、原因、备注和关联证明/附件

### 14.2 历史版本查看

订单详情页的快照版本号需要支持点击查看版本详情。版本详情使用对应配置页面的布局简化展示，直接展示该历史版本的配置值。

配置页面也需要提供历史版本入口。用户可以在基础产品定价、动态调价、行销方案、业务规则等页面查看历史版本列表，并进入版本详情。

历史版本详情的字段命名、分组和展示方式，应尽量与当前配置页面保持一致，避免订单快照里一套命名、配置页面另一套命名。

### 14.3 订单快照原则

订单侧必须保存用于核对和展示的历史信息。开发不能只通过 ID 关联当前主数据后实时读取名称和规则。

需要独立保存的内容包括但不限于：

- 门店名称
- 企业名称
- 客户展示信息
- 车组名称
- 车型信息
- 车辆信息
- 行销方案名称与配置值
- 标准价与动态调价结果
- 服务产品名称与价格
- 业务规则配置值
- 派车规则版本
- 取车、还车、续租、事故等事件发生时的费用计算结果

## 15. 智能调度与派车

### 15.1 派车阶段

门市租车订单的派车分为车组库存占用、车辆预分配和车辆硬锁定。

门市租赁调度对象包含订单、车组库存、具体车辆和履约组织。取车门市所属车行决定该笔订单的履约车行范围。自动派车、人工改派和改还车门市当前只在同车行范围内处理，跨车行不开放。

普通调度、备车、归位和车辆位置调整只改变车辆当前位置，不改变车辆资产所属车行。当前各车行车辆先独立，不做跨车行车辆调拨、跨车行库存池或跨车行车辆借调。订单需要保存实际履约车辆资产所属车行快照，用于车行结算、统计和历史追溯。

待支付订单不进入智能派车。已预约订单可以进入派车池。

企业月结订单只要已预约，也可以进入派车池。企业月结只影响资金链路，不影响车辆派发逻辑。

每笔订单到达规则配置的硬锁定时间时，系统必须执行一次自动分派或预分配有效性复核。复核通过后转为已硬锁；复核失败或没有预分配车辆时，系统立即在可交付车辆池中重新匹配；仍无车可派时进入人工调度队列，订单主状态不变化。

调度边界、同车行跨门市还车和跨车行不支持范围按《门市租赁调度边界与履约规则》执行。

### 15.2 派车状态

车辆派车状态用于表达订单是否已经分配具体车辆：

- 待派车
- 已预分配
- 已硬锁
- 人工改派
- 免费升级

车辆排程看板需要在订单块中展示当前是预分配还是已硬锁，便于门店判断车辆占用强度。

快捷改派执行改派规则，默认只换同车组车辆。需要免费升等时，由人工按免费升等独立操作，不把免费升等混入快捷改派默认逻辑。

### 15.3 自动派车

智能调度按门市、门市下可服务据点、车组、调度占用时长、车辆可用性、车辆状态、订单冲突、车辆评分等条件计算可派车辆。

跨门店调拨和跨车行派车本期不做。系统只在取车门市所属车行范围内、取车门市下可交付车辆中派车。门市租车的可交付车辆来自取车门市下具备门市租车服务能力的据点；24 小时自助租车的可交付车辆来自用户选择的具体自助取车据点。

同车组内订单不再计算独立订单权重公式。系统先按调度占用时长从长到短处理订单，占用时长相同时，再按订单预计金额、预计取车时间和创建时间排序。该口径用于避免高价短订单先切碎低评分车辆时间轴，保持“大石块优先填空”的调度目标。

评分公式参考当前智能调度算法 PRD，重点包含：

- 已行驶里程
- 预计退役里程
- 当月预计营收
- 车辆成本
- 出厂年月
- 当前年月
- 里程权重
- 营收权重
- 车龄权重

当前口径中营收权重为主要权重。权重参数可以配置，评分低者优先派遣。

基准日均里程用于订单分配后估算车辆本轮模拟新增里程，公式为订单租期 × 基准日均里程。该值影响后续车辆评分，不作为同车组订单排序权重。

### 15.4 人工优化

人工优化用于在基础闭环内帮助营运人员重新检查指定时间范围内的派车结果。本期保持简化，不做复杂仿真和跨门店调拨。

人工优化范围：

- 只处理当前门店
- 只处理用户选择的时间范围
- 只处理已预约且需要派车的订单
- 不处理待支付订单
- 不处理已取车订单
- 不处理已还车订单

人工优化需要保护以下订单：

- 已人工改派的订单
- 已免费升级的订单
- 进入临近取车保护期的订单
- 已硬锁且不允许调整的订单

临近取车保护期按硬锁定时间点前固定时间处理。硬锁定时间点由用户在规则中配置，保护期口径为硬锁定时间点前 2 小时。

人工优化结果使用固定原因：

| 原因编码                    | 含义                        |
| ----------------------- | ------------------------- |
| ASSIGN_PENDING          | 待派订单分配车辆                  |
| REPLACE_CONFLICT        | 当前车辆存在冲突，改派到可用车辆          |
| REPLACE_SCORE           | 存在评分更优车辆，执行优化替换           |
| KEEP_CURRENT            | 当前分配已满足规则，无需调整            |
| SKIP_MANUAL             | 人工改派或免费升级订单，本次跳过          |
| SKIP_NEAR_LOCK          | 临近取车保护期内，本次跳过             |
| SKIP_NO_VEHICLE         | 无可用车辆，本次未分配               |
| APPLY_VALIDATION_FAILED | 应用结果时校验失败，未生效             |
| AI_RISK_AVOIDANCE       | AI 基于风险规避推荐调整车辆，应用前仍需系统校验 |
| AI_MANUAL_REVIEW        | AI 建议人工确认，不直接写入派车结果       |
| AI_DATA_INSUFFICIENT    | AI 数据不足，无法完成可靠判断          |

人工优化结果状态使用固定枚举：

- 已优化
- 未变化
- 已跳过
- 失败

### 15.5 AI 调度分析

AI 调度分析是现有智能调度能力上的辅助分析层，不替代规则优化和系统校验。

AI 调度分析初版按“可控辅助分析闭环”处理：不做聊天式多轮 Agent，不做 AI 自动派车，不做自动学习或自动调参。系统必须先完成硬约束候选池过滤，再向模型提交合法候选车辆、不可用原因、系统基线方案和调度风险；AI 推荐车辆必须来自合法候选池。

单次分析仅支持未来 3 / 7 / 14 天范围，最多分析 50 笔订单和 120 辆候选车辆；超出订单上限时不发起模型调用。AI 返回必须符合系统定义的 JSON Schema，系统校验通过并经调度员确认后，才可按现有调度服务逐单应用。

租户需要先在营运平台完成 AI 模型配置，包含模型提供商、API Key、Base URL、模型名称和启用状态。API Key 由租户自行维护，系统加密保存，前端不回显明文。

AI 调度分析系统提示词通过独立提示词配置文件维护。配置文件需要包含全租户默认提示词版本，也可以为指定租户配置专属提示词版本；调用时优先使用租户专属版本，未命中时使用默认版本。租户管理员不在营运平台自由编辑提示词，提示词由平台管理员或系统运维上传、校验和启用。

调度员在车辆排程看板发起 AI 分析时，系统需要同时提交两类内容：

1. 系统提示词，用于声明 AI 的角色、任务、硬约束、输出格式和禁止事项。
2. 调度分析数据包，用于提供订单、车辆、门市、据点、排程、规则、系统基线方案和预计算风险。

AI 只输出风险诊断、推荐动作、推荐原因、信心等级和需要人工确认的事项。AI 不得直接修改订单状态、派车状态、车辆状态、预分配、硬锁、改派、取消、支付、退款或账单。

AI 推荐结果必须经过系统 JSON Schema 校验、分析任务 ID 校验、车辆硬约束校验、订单状态校验、时间窗冲突校验、人工保护校验和权限校验。分析任务 ID 由系统创建 AI 调度分析任务时生成，并随数据包提交给模型；AI 只能原样返回。系统必须校验返回 `analysisId` 与当前任务一致，不一致时整批 AI 结果无效，不进入推荐展示和应用流程。调度员确认后，系统仍按现有调度服务逐单应用，通过校验的订单写入预分配，失败订单跳过并展示原因。

AI 调度分析返回结构需要包含 `data_insufficient` 风险类型和 `AI_DATA_INSUFFICIENT` 原因码，用于表达数据不足、无法完成可靠判断的场景。模型返回的 `summary` 只作为日志参考，页面展示的统计、风险数量、可应用数量和推荐排序由系统重算。

每次模型调用必须记录提示词来源、配置文件版本、提示词版本、完整提示词正文、完整请求数据包、模型原始返回、系统解析明细和系统校验结果。车辆排程看板 AI 分析弹窗提供本次请求日志页签，系统通用参数 AI 模型接入下提供历史调用日志列表。请求日志展示实际提交给模型的内容，但不得展示 API Key、Authorization Header、模型账号密码、会员敏感资料和支付资料。

完整提示词正文、完整请求数据包、模型原始返回和系统解析明细固定保留 180 天。到期后自动清理完整原文，仅保留分析任务 ID、租户、发起人、模型、提示词版本、提示词 Hash、数据包 Hash、隐私过滤结果、校验结果、应用结果、异常原因和操作记录摘要。日志清理不影响订单、车辆排程、费用、操作记录和调度应用结果的业务快照。

AI 不可用、租户未配置模型、模型调用超时或返回格式错误时，现有规则智能优化继续作为兜底能力。

### 15.6 统一排程中心规划

本期门市租车仍按车辆服务类型隔离处理，不实现跨业务线统一排程。

未来规划统一排程中心。统一排程中心在门市租赁开发完成后再规划和开发。统一排程中心按车辆维度展示所有业务线订单和预约占用，分时租赁、门市租赁、公务车等业务都占用同一台车的时间轴。统一排程中心上线后，同一台车辆可以同时支持多个业务线，系统通过时间轴冲突校验决定车辆是否可被不同业务线预约、派车或调度。

## 16. 原型同步原则

PRD 与 HTML 原型需要保持一致。文档新增状态、字段、规则、版本入口、历史版本详情、资金处理方式后，原型中需要至少有对应入口或示例展示。

原型可以不做深度联动，但必须让开发能够从页面上看到该功能的存在方式。

原型同步时重点检查：

- 订单列表是否覆盖主要状态和标签
- 订单详情是否能查看快照版本
- 企业月结订单是否展示月结口径
- 取车页是否区分履约担保和预授权转租金
- 还车页是否区分自付补缴、退款和企业月结挂账
- 费用管理弹窗是否能表达费用组成和处理结果
- 规则页面是否展示默认值、历史版本和版本详情
- 车辆排程看板是否展示预分配和已硬锁

## 17. 当前本期不做或弱化范围

以下内容当前不作为本期主要实现范围：

- 下单全额支付
- 企业月结额度控制
- 跨门店调拨
- 复杂人工派车仿真
- 原型深度联动
- 企业月结费用拆分为企业承担和个人承担
- 订单完成后通过主状态表达追缴

这些内容可以在未来版本扩展，但当前 PRD 和原型不应按已实现处理。

## 18. 后续继续设计时的检查清单

每次修改门市租车相关需求时，需要按以下顺序检查：

1. 是否影响订单主状态或子状态
2. 是否影响个人自付、企业非月结、企业月结三种资金链路
3. 是否影响下单、取车、还车、续租、取消、事故中的任一事件
4. 是否需要新增订单快照字段
5. 是否需要新增配置版本或历史版本详情
6. 是否影响智能调度派车或车辆排程
7. 是否需要同步订单列表、订单详情、规则页面或弹窗原型
8. 是否存在历史订单被当前基础资料变化影响的风险
9. 是否存在费用重复收取、漏收、误退或月结漏挂账风险
10. 是否需要在文档中明确默认值

## 19. 后续 AI 协作时的工作方式

后续 AI 协作门市租车需求时，应先读取本文，再读取当前任务直接相关的 PRD 和 HTML 原型。

编写 PRD 时使用产品经理口吻，文档内容应可直接交付开发，不写“建议”、“可以考虑”、“待确认”这类表达。需要表达未实现范围时，直接写“本期不做”、“本期不支持”、“本期按以下规则处理”。

修改 HTML 原型时，不要求实现完整后端联动，但需要通过示例数据、状态标签、弹窗、历史版本入口或说明文本，让开发能够明确页面需要承载的业务逻辑。

遇到规则冲突时，优先保持以下原则：

- 企业月结不走个人支付链路
- 订单历史信息读取订单快照，不读取当前主数据名称
- 订单费用计算绑定历史规则版本
- 还车结算只处理差额，不重复收取已收租金
- 完成后追缴不改变订单主状态
- 派车逻辑不处理待支付订单
- 跨门店调拨本期不做
