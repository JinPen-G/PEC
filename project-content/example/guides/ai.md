## 连接 MCP 服务

项目 MCP 使用 Streamable HTTP，提供项目需求、治理规则、更新记录与组件源码。管理员在当前项目“AI 接入”中签发读取凭证，将配置添加到支持该传输方式的 Agent 客户端。

```json
{
  "mcpServers": {
    "{{projectId}}": {
      "url": "{{origin}}/api/project-context/mcp",
      "headers": {
        "Authorization": "Bearer <project-read-only-token>"
      }
    }
  }
}
```

用当前项目签发的凭证替换占位符。网页公开浏览和 MCP 的项目读取范围分别管理。

<div><dt><code>get_project_context</code></dt><dd>首先确认项目、版本，以及可读取的需求、治理规则和组件范围。</dd></div>
<div><dt><code>read_project_updates</code></dt><dd>读取平台规范和接入更新；需要项目资料时，再选择对应项目更新。</dd></div>
<div><dt><code>search_requirements</code></dt><dd>按业务问题查找需求，返回匹配内容与原文位置。</dd></div>
<div><dt><code>read_requirement</code></dt><dd>读取具体需求原文及页面关联，按返回游标继续读取。</dd></div>
<div><dt><code>get_requirement_graph</code></dt><dd>读取需求节点、明确关系、原型覆盖和维护状态。</dd></div>

<div><dt><code>get_page_context</code></dt><dd>从一个页面定位其需求与业务说明。</dd></div>

## 工程治理

连接 MCP 后，不仅能获取组件、区块和页面源码，还会获得工程治理指引，帮助 Agent 确认需求、拆分任务、验证结果并做好交接。

- **先明确，再实施**：读现有资料，确认目标、范围和验收，缺少关键信息时逐项询问，已有结论直接沿用。
- **任务与记录各归其位**：按可验收的结果拆任务，保留实际开发记录和最新接续；本地需求文档按需要创建。
- **验证并完成收尾**：保留他人修改，检查更新与依赖，记录实际验证和未完事项，清理自己的临时环境。

这套方法可以单独用于你的工程。Agent读完后会说明采用方式、询问是否遵循，再按实际工作给出自查结果；没有需求资料或不安装组件，也可以使用。

### 1. 确认需求依据并检查更新

这是一套可以独立采用的工程治理方法，适用于已有工程、组件接入和使用Agent开展的开发任务。采用它不要求使用特定平台的需求，也不要求先建立一套新文档。

开工前找到负责人认可的需求依据：可以是现有PRD、任务系统、已确认的对话或其他正式资料。记清来源、位置、版本、确认状态和验收条件。草稿、规划与历史资料保持原状态，不因Agent读到就视为已批准。

本地需求文档可建可不建；已有可靠来源时保留引用即可，副本注明来源。出现差异先核对原依据，需求冲突、未说明的业务规则或新增范围交由负责人确认，不用本地整理稿或代码现状反向改写需求。

开始、恢复或继续开发前，检查工程的更新记录、已有接续，以及所采用规范和组件的版本变化。更新记录帮助发现变化，验收仍回到原需求。通过MCP读取时沿`nextOffset`读完，保持返回的版本一致；未发布、无权限、失败与截断分别说明，不当作“没有变化”。

### 2. 先理解任务，已有结论直接沿用

Agent先阅读目标工程现有资料和已确认需求，明确使用者、业务规则、实施范围和验收条件。资料中已有的答案自行核对；关键问题仍不清楚时，一次只问一个，达到约九成把握理解目标后再给方案。

例如，开发订单导出前，应从原文核对谁能导出、哪些记录和字段、时间范围及异常处理。缺少必要规则时提出具体缺口；目标与授权已经明确就继续完成，不反复确认已回答的事项。

### 3. 长期规则只有一个入口，需求与工程记录各归其位

在目标工程已有规则入口中记录采用的规范及来源；使用`AGENTS.md`时，其他工具入口引用同一份。根README介绍工程与运行方式，文档导航负责找到专项，不记录对话临时进度。保留工程原有规则，遇到冲突先说明具体条款和影响。

按需求、任务、记录、接续四种职责管理资料。本地需求文档可选，任务、记录和接续沿用目标工程现有形式，不为了文件齐全重复建档。

```text
AGENTS.md
README.md
docs/
  文档导航.md
  订单管理/
    订单管理-需求.md       （可选：已确认需求或来源引用）
    订单管理-开发任务.md
    订单管理-开发记录.md
    订单管理-协作接续.md
```

| 资料 | 写清什么 | 更新时机 |
| --- | --- | --- |
| 需求依据 | 需求来源、原文位置、版本、状态与验收；本地副本注明来源。 | 负责人确认变化后核对并同步。 |
| 开发任务 | 稳定任务ID、来源需求、前置依赖、实施约束、验收条件和有证据的进度。 | 获准增加任务，或阶段达到原验收门槛时。 |
| 开发记录 | 完整阶段改动及原因、实际验证、失败与剩余问题、必要证据。 | 一个完整功能阶段结束时。 |
| 协作接续 | 当前目标、文件归属、需求与更新版本、未完事项、下一入口及已验/未验范围。 | 现场改变或交给下一位Agent时。 |

技术设计和部署约束进入任务，测试及评审证据进入记录。不要另建“最新计划”“最终方案”“移交报告”重复维护同一件事。公共规范、模块README和更新日志按实际用途维护。

### 4. 按可验收的行为拆任务

任务绑定已确认需求的具体条款，按可交付行为拆分，不按修改文件数量估算进度。以下是写法示例，不会自动给工程增加任务：

| 任务示例 | 前置与内容 | 完成条件 |
| --- | --- | --- |
| EXP-01 核对导出需求 | 读取来源需求和更新，核对角色、筛选、字段及脱敏要求。 | 必要口径有依据，未确认项明确列出。 |
| EXP-02 完成导出链路 | 依赖EXP-01，连接页面、服务端校验和文件输出。 | 授权角色取得符合原需求的文件，失败有真实提示。 |
| EXP-03 验证与收口 | 依赖EXP-02，验证越权、空结果和关键异常。 | 原验收逐项有证据，未验环境和剩余问题写清。 |

已确认的编号、范围、依赖、顺序和验收不因实现方便而改变。没有量化门槛时使用“未启动、进行中、待核实、完成”；有既定分档时按原门槛更新，不根据代码量或测试数量推算完成率。

### 5. 开工核对现场，协作明确写入者

每天首次修改与跨日继续前，核对实际目录、分支、HEAD、工作区、暂存区、合并/挑拣状态及远端。读最新接续和相关更新记录，确认自己和其他人的成果归属。

同一公共文件或接口明确一个写入者；并行成果按固定提交或补丁整合，核对依赖和消费者。保留他人的未提交修改，不用reset、clean或整树覆盖清场。工作树按需准备，不复制整套依赖、数据库、缓存与构建产物，也不跨树链接可写依赖。

接续应能让后来者直接找到下一步：

```text
当前目标：完成订单导出。
需求来源：需求ID或链接、原文位置、已核对版本。
更新检查：已读更新版本、相关变化及需要重验的范围。
写入归属：本任务负责的接口与页面；公共合同的维护者。
已完成：实际结果及开发记录入口。
未完成：尚未满足的原验收条件。
下一入口：具体文件、函数或待复现操作。
验证边界：已验证与尚未验证的角色、场景和环境。
```

### 6. 读取完整源码，沿工程链路实现

MCP同时提供组件、区块和页面源码。先用`list_components`查找已上架条目，再用`get_component`取得文件、目标路径、npm依赖和`registryDependencies`；用`read_component_file`逐文件读完需要的源码、样式与辅助模块，递归核对登记依赖。文件分页沿`nextOffset`读取并保持`registryRevision`一致，不能只拿到入口文件就声称源码完整。

源码是实现参考，业务行为仍核对已确认需求。接入目标工程前检查目录、主题、依赖、字段、校验、状态、交互和异常，标明需要替换的模拟数据。保留第三方来源、原始版本与许可；可复用组件和页面与平台外壳、账号数据及私有配置分开维护。

修改前检查入口、调用方、公共协议、权限、存储与外部副作用。接口同时核对生产者和消费者，权限在服务端校验。沿用已有组件、主题和分层；复杂分支和写入边界用简短注释说明职责与原因，功能修改与全量格式整理分开。缺失、失败、权限拒绝分别呈现，不用空数组、零值或模拟成功遮住问题。

### 7. 需求、页面与图谱一起核对

读取需求后检查相关图谱的原文出处、关系、原型覆盖及维护提醒。只有明确PRD原文支持的关系才可作为业务依据，图上的距离、颜色和同类归属不表示业务依赖。

采用图谱的工程，在需求或原型新增、修改、删除、重命名时同步核对图谱；无影响也记录检查依据。先核实章节、引文和呈现位置，再登记review并运行检查，不全量刷绿。读取外部资料时记录差异和影响，不把猜测写成正式规则。没有图谱时标明不适用，不为套用规范凭空生成关系。

### 8. 阶段验证留下真实证据

按修改范围选择必要验证：文档检查内容、链接与格式；逻辑修改覆盖实际回归；界面修改检查浏览器交互和布局。运行命令前读脚本与参数，不能凭test名称认定只读或离线。

```text
本阶段目标与来源需求：
实际改动与原因：
验证命令和退出码：
覆盖的角色、场景与环境：
失败、未完事项和下一步：
证据位置：
```

失败修复后复验相关范围；无新修改或明确风险不反复扩大测试，不删除断言、跳过失败或降低门槛。静态检查、类型、单测、构建、浏览器、外部集成、用户验收和正式发布分别报告。

### 9. 结束阶段就更新接续，按授权同步Git

阶段结束对照原任务验收，把有依据的进度写回任务，完整证据写入记录，接续覆盖为当前现场；任务不堆测试流水，接续不追加相互冲突的“最新”指令。

已有日常提交和普通推送授权时，及时同步归属明确的成果，逐文件核对后暂存，推送后读取远端确认包含提交。未完成的检查点放在自己的任务分支并标明缺口。采用治理不会新增提交、合并、强推或部署授权，已有授权也无需反复询问。

### 10. 临时环境由创建者清理，问题保留到解决

创建测试库、脚本、独立构建或浏览器验证前，明确创建者、单一任务目录和退出清理方式。纯文档与只读任务不安装依赖，重复验证复用本任务环境。

成功、失败、超时和取消均释放本任务独占的进程与一次性文件。保留必要版本、命令、退出码和少量证据后清理；原稿、共享库、在用依赖与他人成果不能当作垃圾。删除或移动前核实绝对路径、归属、占用和链接，完成后核对结果。受阻时如实登记位置、数量、原因与处理条件，不换工具绕过禁令，不把“已归集”说成“已删除”。

开发记录保留最近一个月，较早的完整阶段按月归档；精简或移动前保全原文、SHA-256和去向，修复现行链接。未解决事项继续留在当前记录与接续，不因归档或目录整理把任务标为完成。

### 11. 说明采用方式，再自查实际工作

Agent读完规范后，向当前开发者简要说明需求确认、任务与记录、协作归属、验证和收尾的方法，并询问：

```text
是否在你的工程中采用这套治理规范？
```

已有采用、部分采用或拒绝选择时直接沿用。连接、读取和沉默不算同意；拒绝不影响原有资料读取。采用后在允许访问的目标工程先对照规则、Git现场及已有文档，按采用范围补齐，需求文档可建可不建。选择保留在对话或获准维护的本地规则中，MCP不登记采用状态，也不上传目标工程内部资料。

| 检查项 | 状态与依据 | 下一步 |
| --- | --- | --- |
| 需求来源与更新是否已核对 | 附需求ID、原文位置、资料及更新版本。 | 标明变化与需重验的内容。 |
| 目标、验收与写入归属是否明确 | 附原条款、工程规则和Git现场依据。 | 列出具体缺项或冲突。 |
| 任务、记录和接续是否各归其位 | 附实际文档；未建本地需求时附已确认的来源引用。 | 沿用已有资料补缺。 |
| 源码、依赖、验证与清理是否完整 | 附清单、源码版本、验证结果及残留情况。 | 保留未验和受阻事项。 |

每项使用“已遵循／待补齐／有冲突／无法核实”并附证据。看不到工程或未执行验证时不能回答“全部遵循”。MCP提供规范和引导，具体执行由当前开发者与Agent完成。

## 让 Agent 先读取规则

1. ### 读取规范和更新

   调用`get_project_context`查看可用能力，用`list_governance_rules`和`read_governance_rule`读完通用规范，并用`read_project_updates({source: "platform"})`检查规范与接入更新。

2. ### 读取规范并说明采用方式

   Agent简要说明需求确认、任务与记录、协作、验证和收尾的方法，再询问是否采用；已有选择直接沿用。

3. ### 在目标工程中执行和自查

   以负责人认可的需求依据开展任务，保留已有规则和成果，按需要补齐任务、记录与接续，并用证据说明哪些已遵循、待补齐、有冲突或无法核实。

规则和更新记录都要按返回游标读完，保持各自版本一致。MCP提供引导，实际执行由当前Agent完成。

## 读取页面源码

使用`list_components`查找已上架的组件、区块或页面，`get_component`取得文件、npm依赖与`registryDependencies`，再用`read_component_file`读完源码、样式和辅助文件。页面以页面级区块提供；依赖也要继续读取，文件分页保持同一`registryRevision`。

公开区块也可以通过 shadcn CLI 安装：

```sh
npx shadcn@latest add {{origin}}/r/{{projectId}}/<registry-item>.json
```

安装步骤与示例导入见[使用指南](usage.md)。

## 选择读取范围

1. ### 创建项目凭证

   在要读取项目的 AI 接入中，为当前工具或工作场景创建凭证。

2. ### 勾选需要的能力

   `business:read` 用于需求和图谱，`governance:read` 用于已发布治理规则，`components:read` 用于源码与安装清单。

3. ### 配置客户端

   将凭证保存在客户端私有配置中。过期或撤销后更新配置，不把凭证写入源码或分享链接。

## 可读取的上下文

- **业务需求**：项目概况、PRD 原文、页面要点与完整说明。
- **功能关系**：前置条件、功能关联、数据流转与平台接口关系。
- **组件与页面源码**：已登记组件、区块和页面的源码、样式、辅助模块及依赖。
- **更新记录**：与网站同版的项目更新，用于发现变化并回到需求原文核对。
- **工程规则**：可独立采用的通用规范，以及凭证允许读取的补充条目。

读取结果有游标时继续分页；出现维护提醒或原文冲突时，保留差异并核对来源。图中的距离和颜色不作为业务依据。
