# Preview 工程治理规范

版本：1.1。维护日期：2026-11-12。适用范围：Preview 自有平台代码、工具和工程文档。项目业务 PRD 由所属项目管理。

## 依据与职责

治理方法参考 Rental OS 的共用 AGENTS、四册职责、工作树与临时产物生命周期、Git 同步及验证方法。Preview 的业务目标由负责人确认，技术规则按本仓库实际边界制定，不照搬其业务、任务分档、技术选型和持续执行授权。来源版本与适配证据保存在维护者的本地工程记录。

本轮授权决定当前可做事项；需求定义产品目标；任务定义获准工作及验收；公共规范定义实现约束；代码反映当前实现；记录提供阶段证据；接续定位下一入口。发现冲突时记录原条款与代码事实，不能用新日期或代码现状自动推翻已确认要求。

维护者的本地工具规则保存在AGENTS和CLAUDE，公开工程方法由本规范说明。[README](../../../README.md)介绍工程，[文档导航](../../文档导航.md)索引正式资料，两者不维护活动进度。

PM 在现有专项内组织范围、依赖、写入归属和验收，不另造跨专项进度总账。涉及公共文件时确定唯一写入者；并行成果按固定版本接收，整合前核对依赖和未完项。记录中的旧派工只作为证据。

## 专项四册

| 文档             | 应包含                                              | 不应包含                          |
| ---------------- | --------------------------------------------------- | --------------------------------- |
| 主题-需求.md     | 目标、角色、场景、范围、确认来源、验收和待决策项    | 日常流水、猜测的已完成功能        |
| 主题-开发任务.md | 稳定任务 ID、依赖、实施与兼容约束、验收、有据进度   | WIP、测试/修复/提交流水、临时提醒 |
| 主题-开发记录.md | 完整阶段变更、实际命令/退出码、证据、问题、未验边界 | 每次工具调用、重复百分比总表      |
| 主题-协作接续.md | 当前目标、写入范围、状态、缺口、下一入口、验证边界  | 历史全流水、复制的全套任务表      |

正式专项根目录只放这四份现行 Markdown。技术方案与部署/回退约束并入任务册，评审与验收结果并入记录，接手说明并入接续。独立子专项在有实际独立需求和归属时另建四册；不能为文件齐全虚构任务、完成度或立项。

公共规范、实际模块 README、索引、发布变更记录、机器可读契约、模板和示例按用途维护，不套四册。四册已经能导航的专项目录不另建重复 README。未来设计只放方案、映射、前置与回退条件，不夹当前进度，也不借“未来规划”隐藏当前实施工作。

Preview 的平台工程四册与 `project-content` 中明确发布的业务需求、指南和治理资料属于不同发布范围。整理内部规则不把 AGENTS、研发记录或接续加入 MCP/网页业务白名单。

## 任务与进度

任务 ID 一经建立，不因改名、归档或合并变更含义。修改范围、依赖、优先级、验收门槛必须有负责人新的明确依据。

需求、任务正文和已确认技术规范保持批准依据。日常只更新受影响任务的有据进度及证据引用；完整阶段收口时逐项复核原门槛，未满足的条件写入记录。新一轮治理工作使用新任务身份，不重开或改写已完成的历史任务来套当前进度。

任务进度由原验收门槛决定；没有量化规则时用未启动、进行中、待核实等状态。文件数、行数、截图数和测试数量不构成产品完成率。100% 仅表示该任务列出的全部门槛满足，并引用记录中的实际证据；不得换算成全平台已上线。

实现结论必须区分代码实现、自动化验证、浏览器行为、用户视觉验收、真实外部集成和发布。示例登录不是账号认证，静态构建不是具备项目授权的远程服务。

## 阶段记录与协作接续

按完整功能阶段更新开发记录，记录问题、结果、关键提交、命令、退出码和适用范围。近期区保留最近一个月；更早的完整阶段先原文移入所属专项的 `历史归档/开发过程/YYYY-MM.md`，再移出近期区，活动问题仍留现行摘要、具体条件与证据链接。没有超期阶段时不为了目录齐全建立空归档。

接续覆盖更新当前现场，不在末尾无限堆“本轮”“继续”“最新”。保留正在处理的目标、写入归属、未知 WIP、前置缺口、下一文件/函数和已验/未验范围。自动归档、定时更新和并行派工不由文档本身授予。

归并接续或任务流水时，逐项核对以下内容去向：尚未通过的原验收、业务冲突、待同步成果、外部环境缺口、临时残留及原处理限制。阶段详情归记录，接续保留当前摘要和入口；不能只给一个历史快照链接就丢掉活动问题。

## 命名、迁移与历史

- 正式文档采用“主题-类型.md”；版本、日期、状态放正文。目录按平台能力、公共技术资料和归档组织，不使用流水编号掩盖归属。
- 归并前保全原文字节，清单记录原 source、SHA-256、固定 Git 对象或必要快照、原因与内容去向。已提交且同字节的内容不再复制一份；未提交或工作区字节不同的内容保留必要快照。历史副本不修改，相对链接按原 source 解释。
- 修复所有受影响的现行链接；未解决问题不能只留历史。纯目录整理不修改需求、任务身份和验收状态。
- 不建立按文件逐一重复的说明书。复杂模块有必要时补 README，说明入口、领域服务、存储/适配、消费者和验证入口，并从导航可达。
- 未知 WIP、删除状态、品牌原稿、历史产物和项目资料保留现场。清理须核对实际引用、归属和范围。

## 阶段收口

1. 核对改动是否仍在本轮范围内、公共文件归属是否清楚，需求和原任务门槛有无被误改。
2. 按实际源码与参数选择最小必要验证；失败保留反例，结果区分静态、类型、行为、构建、浏览器、真实集成、正式验收和发布。
3. 把完整阶段证据写入已有记录，按原门槛更新任务进度，覆盖接续中的旧现场；需求/PRD/原型相关修改同时核对业务图谱，内部治理改动也记录具体无影响依据。
4. 固化最小证据、处理本任务临时环境和新增残留，按维护者本地规则核对路径、归属与临时文件生命周期。既有测试仍使用系统临时目录；本次规范不声称已改造全部脚本或清理历史残留。
5. 按Preview的实际授权提交已核对的平台文件并处理同步，核对远端证据。文档落地、Git 同步、业务验收和生产部署分别报告。

## 可执行检查

`npm run docs:check` 检查当前工程文档的本地 Markdown 链接、npm 命令和已登记专项四册；历史归档不参与现行链接校验。它不联网，不验证 Markdown 锚点、HTML 超链接、业务完成度或文档是否获得批准。

`npm run architecture:check` 检查声明的源码层间导入方向；它不执行业务代码，不等同于服务端权限、安全隔离或完整依赖图审计。

检查器源码变动必须覆盖能暴露问题的反例，不能只断言自己的输出。质量门禁与运行副作用见[测试指南](Preview-测试指南.md)。
